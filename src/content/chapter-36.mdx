## 1. Deploy a service, not just a model call

**Deployment** makes an application version available in an environment. **Operations** keeps that service functioning over time. A hosted model API operates the model for you, but you still own your application, account permissions, retrieval data, user experience, and failure handling. A self-hosted model also makes you responsible for model serving capacity and infrastructure.

<OperationsDiagrams kind="service" />

For the movie assistant, a browser sends a request to a backend API. The backend checks identity and inputs, retrieves permitted movie facts, calls the model, validates the result, and returns a response. Persistent data such as watchlists belongs in an appropriate store. Long-running catalog ingestion can use a queue and worker so a browser request need not wait for the entire job.

A **container** packages an application and its runtime dependencies into a deployable unit; it does not include every external service or guarantee isolation by itself. A managed application platform, virtual machine, or container service can run that unit. Serverless execution can simplify operations for suitable workloads, but time limits, cold starts, and connection handling still affect behavior. Choose the smallest setup that meets the application's requirements.

Keep secrets on the backend, supplied through a secret manager or protected runtime configuration. Use separate development, staging, and production environments, credentials, and data access. OpenAI's [production guidance](https://developers.openai.com/api/docs/guides/production-best-practices) discusses secret handling, scaling, and ongoing model operations; this chapter's design is provider-independent.

## 2. Version everything that can change behavior

A release is more than a Python file. The same code with a new prompt, model configuration, or index can produce different answers. Keep a **release manifest**: a record connecting a deployable artifact to the versions and settings used to evaluate it.

| Record | Movie-assistant example |
| --- | --- |
| Application and dependencies | Code revision, dependency lockfile, built image digest. |
| Model and generation settings | Provider/model identifier, sampling settings, output limit. |
| Prompt and policy | Recommendation instructions, tool schemas, permission rules. |
| Retrieval and data | Catalog snapshot, chunking/embedding configuration, index version. |
| Runtime configuration | Timeouts, retry limits, feature flags, routing rules. |
| Validation evidence | Test results, evaluation dataset version, known limitations. |

Use a model snapshot identifier where the service supports one; record unavoidable moving dependencies and retest changes. A pinned identifier improves change tracking but does not make stochastic outputs identical. Validate required configuration at startup, and keep secret values out of manifests and logs.

**Continuous integration (CI)** builds and checks a change. **Continuous delivery** keeps a checked artifact ready for release; **continuous deployment** automatically releases changes that pass the configured process. Promote the tested artifact across environments rather than rebuilding an unknown variant at the final step. Keep infrastructure and configuration changes reviewable too.

<details className="optional-depth">
<summary>Go deeper: rollback needs compatible state</summary>

Restoring yesterday's application is unsafe if today's database migration removed a field it still requires. Use compatible staged migrations: add new structure, support the transition, move usage, and remove obsolete structure only when old versions are no longer needed. Version indexes and retain a tested switching path where practical. A rollback changes future behavior; it does not undo messages already sent, watchlist edits already made, or corrupted data. Backups need tested restoration procedures, not just a successful “backup created” log line.

</details>

## 3. Release gradually and keep a recovery path

Start with unit and integration checks, chapter 34's quality evaluation, and chapter 35's security checks. Staging should exercise the real configuration shape and important integrations using controlled data. Run a **smoke test** for a small set of essential actions after deployment; test load separately to find capacity and latency limits.

<OperationsDiagrams kind="release" />

| Release pattern | How it works | Important limitation |
| --- | --- | --- |
| Rolling update | Replace instances progressively. | Old and new versions coexist; interfaces must remain compatible. |
| Blue-green | Keep two environments and switch traffic. | Extra capacity and shared-state compatibility still matter. |
| Canary | Send a limited share to the candidate and inspect outcomes. | Small or biased samples can miss serious defects. |
| Feature flag | Enable or disable a capability through configuration. | Flag combinations need testing and eventual cleanup. |

Set observation periods and stop criteria before rollout. Compare candidate and baseline quality, errors, latency, cost, and important user slices. Google's [canary-release guidance](https://sre.google/workbook/canarying-releases/) explains how limited exposure can reduce the impact of a faulty release. A passing canary reduces uncertainty; it cannot establish that every user scenario works.

<details className="optional-depth">
<summary>Go deeper: representative traffic and observation time</summary>

Assign traffic consistently at the appropriate unit, such as user or session, when switching versions mid-conversation would be misleading. Check language, region, device, and difficult-task coverage. Some failures emerge only after caches expire or background jobs run, so five quick successes cannot justify universal promotion. A shadow run can compare outputs without showing them to users, but must isolate writes and protect user data. Our lab uses fixed request slots and immediate quality labels for reproducibility; real rollout evidence is often delayed, incomplete, and noisy.

</details>

## 4. Observe the request from arrival to outcome

**Metrics** summarize measurements, **logs** record events, and **traces** connect the steps of a request. A trace contains **spans** for operations such as catalog search and a model call. A correlation or trace ID helps connect the relevant records. These signals are described in [OpenTelemetry's documentation](https://opentelemetry.io/docs/concepts/signals/).

For “Find a calm movie under 100 minutes,” record the release identifier, retrieval duration, model duration, retries, token usage, validation result, and final outcome. Do not store full private conversations merely because tracing supports them. Minimize logged content and apply access and retention rules.

| Signal | What it reveals |
| --- | --- |
| Request volume, errors, queue length | Demand, failures, and work accumulating. |
| Time to first response and total completion time | How quickly the interaction starts and the task finishes. |
| Task quality and unsupported answers | Whether successful-looking responses actually help. |
| Token usage, attempts, and cost per task | Where resources are spent, including failed work. |
| Retrieval freshness and tool outcomes | Whether dependencies supply current facts and perform intended actions. |

HTTP 200 means the transport operation succeeded under that endpoint's contract; it does not prove that a recommended film meets the user's constraints. Combine operational measurements with sampled, reviewed quality checks. An average can hide slow requests, so inspect distributions and percentiles as well.

<details className="optional-depth">
<summary>Go deeper: useful telemetry without unbounded labels</summary>

Metric labels create separate time series. A small set of version or status labels can be useful; putting every unique prompt or user ID in a metric label can create unbounded cardinality and expose personal data. Use access-controlled traces or logs for individual investigation, with sampling and retention appropriate to the task. Preserve failure counts independently of trace sampling. Distinguish a missing observation from a successful request, and avoid logging secrets in error messages or exported reports.

</details>

## 5. Define service objectives and error budgets

A **service-level indicator (SLI)** is a measurement of service behavior. A **service-level objective (SLO)** is the target for that indicator over a defined window. A **service-level agreement (SLA)** is an external agreement that may specify consequences. They are related, but not interchangeable. Google's [SLO workbook](https://sre.google/workbook/implementing-slos/) emphasizes measurements that reflect the user experience.

For our teaching example, a **good request** returns a correct movie recommendation within the selected total deadline. The target is at least 95% good requests in the simulated 20-request window. All requests count, including errors and timeouts.

$$
\text{good-request SLI}=\frac{\text{good requests}}{\text{eligible requests}},\qquad
\text{allowed bad requests}=N(1-\text{SLO target}).
$$

At $N=20$ and a target of $0.95$, the **error budget** allows one bad request. Nineteen good requests meet the target exactly; sixteen do not. Four bad requests leave a budget balance of $1-4=-3$: the allowance has been exceeded by three. The 95% target and tiny window are teaching choices, not production recommendations.

Define how the budget affects decisions, such as slowing feature releases while reliability is repaired. A release can also have stricter stop criteria: our lab rolls back on a known bad candidate result even when the overall SLO is still met. The budget is not permission to cause a security breach. Real services need representative volumes, defined exclusions, appropriate windows, and explicit treatment of delayed quality labels.

## 6. Recover without amplifying failures

A **timeout** limits waiting for an operation. An overall **deadline** limits the complete request, including earlier work and retries. A **retry** repeats a failed operation; **backoff** waits between attempts, and **jitter** varies that delay so many callers do not retry together. Bound attempts and total time, and check existing SDK retry behavior to avoid multiplying retries across layers. [AWS's retry guidance](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html) explains this load amplification risk.

<OperationsDiagrams kind="retry" />

Retry only failures that may recover and operations that can be repeated safely. Authentication failures, invalid inputs, and policy denials usually require a different response. Follow the dependency's error semantics and any applicable retry delay. An unsuitable recommendation returned with HTTP 200 is a quality problem, not automatically a transport retry.

For a write, a timeout does not tell you whether the server already applied the change. Use a stable idempotency key and result reconciliation where supported so retrying a watchlist addition does not duplicate its effect. Keep authorization checks in place. A client timeout also does not guarantee that a provider stopped processing or billing.

<details className="optional-depth">
<summary>Go deeper: circuit breakers and graceful degradation</summary>

A circuit breaker can stop sending calls to a repeatedly failing dependency. In the closed state, calls flow; in the open state, they are rejected quickly; in a half-open state, limited probes test recovery. Configure thresholds and recovery behavior from evidence. A fallback might offer a clearly labeled catalog-only recommendation when personalized generation is unavailable. Evaluate fallback quality and permissions too; do not silently treat stale availability as current. Avoid swapping to an untested provider that changes privacy or output behavior. The lab demonstrates bounded retry and rollback, not a circuit breaker or fallback implementation.

</details>

## 7. Control capacity, latency, and cost together

**Horizontal scaling** adds service instances; **vertical scaling** gives an instance more resources. More backend instances cannot overcome an unchanged provider quota. Limit concurrency, use bounded queues, and apply **backpressure** so upstream callers slow down or receive a clear busy response when the service cannot keep up.

| Technique | Benefit | What to verify |
| --- | --- | --- |
| Result caching | Reuses a valid previous answer. | User permissions, region, catalog version, and freshness belong in the design. |
| Prompt-prefix caching | Can reduce repeated prefix processing in supported services. | It does not reuse or guarantee the final answer. |
| Batching | Groups suitable work for efficiency. | Waiting for a batch can increase latency; not all APIs offer the same behavior. |
| Streaming | Shows output as it arrives. | Faster first text does not mean the task has finished successfully. |
| Smaller models or shorter context | Can reduce resource use. | Rerun quality and safety evaluations for the change. |

Track cost per attempted task as well as cost per successful task. Include retries, failed calls, retrieval, storage, observability, and infrastructure where relevant. Set spending controls that actually enforce the application's policy; a notification alone does not stop traffic. Load-test realistic prompt lengths and tool paths, not only the shortest successful request.

For long jobs, return a job ID, expose status, and design cancellation, retry, and completion handling. Bound queue size and job lifetime so a temporary outage does not create an unmanageable backlog. The simulator uses fictional attempt units and sequential requests; it does not predict a provider's price or your production capacity.

## 8. Operate with health checks, runbooks, and feedback

Distinguish **liveness** from **readiness**. Liveness asks whether a process needs restarting; readiness asks whether it can currently receive traffic. Startup checks allow initialization time. A brief model-provider outage should not necessarily restart every healthy application process. Kubernetes documents these [different probe purposes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/); the distinction is useful beyond Kubernetes.

An actionable alert identifies user impact, the affected service, and the responsible owner. A **runbook** gives concrete diagnosis and recovery steps: inspect the deployed version and failing dependency, reduce exposure, verify recovery, and communicate status. Page someone for urgent impact; use a lower-urgency channel for trends that can wait.

In our movie example, wrong recommendations only on the new release suggest investigating that release. Provider errors on both old and new versions suggest a shared dependency. Rollback can contain the first problem while leaving the second untouched. After recovery, record the cause and contributing conditions, add regression cases, and update the runbook. Keep data/index refreshes, credential rotation, and dependency changes in the same controlled process.

<details className="optional-depth">
<summary>Go deeper: drift and training-serving consistency</summary>

Data drift means the input distribution changes; concept drift means the relationship between inputs and the desired outcome changes. For example, a growing share of regional-language requests changes the workload, while changing viewer tastes can change what counts as a good recommendation. Drift is a signal to investigate, not an automatic command to retrain. Training-serving skew occurs when training and production features or transformations differ. Preserve feature definitions, preprocessing, and data validation across both paths. Monitor labels and quality when they become available, investigate shifts, and evaluate a proposed fix before deployment. Google's [production ML monitoring material](https://developers.google.com/machine-learning/crash-course/production-ml-systems/monitoring) discusses these consistency and monitoring concerns.

</details>

## 9. Run the Python operations workbook

The four files are `operations.py`, `data.json`, `test_operations.py`, and a README. Python's standard library is sufficient. You are running a deterministic controller over authored requests; no model, network, cloud deployment, real billing, or watchlist modification occurs.

```bash
python operations.py
python operations.py --rollback observe
python operations.py --share 100
python operations.py --scenario provider_fault --rollback observe --retries 0
python operations.py --scenario provider_fault --rollback observe --retries 1
python operations.py --scenario provider_fault --rollback observe --deadline 1200
python -m unittest -v test_operations.py
```

Read `run_request()` to follow attempt timing and the shared deadline. `evaluate()` routes four windows of five requests, checks candidate outcomes at each window end, and applies rollback to later windows. `summarize()` counts all final results; p95 uses the nearest-rank convention from chapter 34, including failures.

In the bad-release scenario, candidate slots 1 and 3 have incorrect recommendation labels even though the response status is 200. In the provider-fault scenario, slot 1 fails once and can recover; slot 3 fails on both attempts for either version. Backoff is a fixed 200 ms. Every attempted call consumes its full fictional reserved cost, including timeouts. Immediate quality labels and fixed routing are simplifications; they cannot establish real-world reliability or statistical confidence.

## 12. Revision and the next connection

Follow the operating loop: **version → test → release gradually → observe → contain failures → improve**. Measure useful outcomes, keep deadlines and budgets explicit, and make recovery a tested capability. A working demo becomes a dependable service through repeated evidence and controlled change.
