## 1. Follow a request through an application

Imagine the first piece of our personal learning assistant: enter a note ID and receive the matching study note. Several pieces cooperate:

- The **frontend** displays the form and result. It runs in the user's browser in this example.
- The **backend** receives the request, checks it, and coordinates the lookup. It runs as a separate program.
- The **lookup service** finds the requested note in an authored collection. Later, a model can support other operations, such as generating explanations.
- A **database** stores records that need to outlive a single request.

<SoftwareDiagrams kind="layers" />

These are responsibilities, not necessarily four computers. A frontend and backend can both run on your laptop. In the starter, a Python client replaces the form, and that client saves the result locally.

The collection contains three short notes. **N01** is “Overfitting,” with an estimated study time of **20 minutes**. The service returns its authored text by exact ID. This is ordinary software: no model, semantic search, or RAG is involved yet. The time is an illustrative planning estimate, not a promise of understanding.

<details className="optional-depth">
<summary>Go deeper: library, framework, SDK, and service</summary>

A **library** provides reusable code that you call. A **framework** provides an application structure and calls your code at defined points. An **SDK** bundles tools or libraries for working with a platform, often including its API client. A **service** is a running program that other programs can contact. A service must be running before a client can contact it. Importing an SDK and calling a remote operation are separate steps.

## 2. Read an API request as a contract

An **API**, or application programming interface, defines how software can interact. A Python function has an interface too. A **web API** exposes operations over a network, often using HTTP, the request/response protocol used on the web.

The **client** sends a request; the **server** handles it and returns a response. An **endpoint** identifies an operation, such as <code>POST /notes/lookup</code>. Read this simplified HTTP/1.1-style message:

```http
POST /notes/lookup HTTP/1.1
Host: 127.0.0.1:8765
Content-Type: application/json

{"note_id": "N01"}
```

The **method** is POST. The **path** is /notes/lookup. **Headers** describe the message; Content-Type says the body contains JSON. The **body** carries the input. HTTP libraries add framing headers such as Content-Length for you.

In <code>http://127.0.0.1:8765/notes/lookup</code>, the scheme is HTTP, the host is your own computer's loopback address, and port 8765 selects the listening service. A remote API might use a domain name and **HTTPS**, which encrypts transport and authenticates the server through certificates. It does not establish that returned content is correct.

**GET** usually retrieves a resource; **POST** submits data for processing or creation. PUT replaces a resource, PATCH changes part of it, and DELETE requests removal. Our teaching endpoint uses POST to process a JSON lookup request without changing server data; GET would also be a natural design for retrieving a note. Read the endpoint’s actual contract rather than guessing its effects. A query string, such as <code>/notes?limit=20</code>, supplies URL parameters separately from a JSON body. See [MDN's HTTP overview](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview).

## 3. Separate JSON syntax from data meaning

**Serialization** converts in-memory values into a transferable representation. JSON encodes objects, arrays, strings, numbers, booleans, and null as text. **Parsing** turns that text back into values.

```python
import json

body = json.dumps({"note_id": "N01"}).encode("utf-8")
decoded = json.loads(body.decode("utf-8"))
assert decoded["note_id"] == "N01"
```

UTF-8 is the text-to-bytes encoding used here. Python dictionaries are not wire messages: the request carries bytes. JSON uses double-quoted keys and strings, and <code>true</code>, <code>false</code>, <code>null</code> rather than Python's <code>True</code>, <code>False</code>, <code>None</code>. See [Python's JSON reference](https://docs.python.org/3/library/json.html).

A **schema** describes the expected structure and constraints. Our request needs a string <code>note_id</code> matching N followed by two digits. The response contains <code>note_id</code>, nonempty <code>title</code> and <code>text</code>, an integer <code>estimated_minutes</code> from 0 to 1,440, and <code>source_version</code> equal to notes-v1. The client also checks that the returned ID matches the requested one.

| Input | Valid JSON? | Valid for this request? |
|---|---|---|
| <code>&#123;"note_id": "N01"&#125;</code> | Yes | Yes |
| <code>&#123;"note_id": 3&#125;</code> | Yes | No: number instead of string |
| <code>&#123;"note_id": "unknown"&#125;</code> | Yes | No: wrong ID format |
| <code>&#123;"id": "N01"&#125;</code> | Yes | No: the required field is missing |

Validate at boundaries, where data enters or leaves your code. A response with status 200 and valid JSON can still have the wrong fields, units, or values. Even a valid schema cannot prove that the note’s explanation is accurate. A well-formed but absent ID, such as N99, gets 404 rather than 400.

<details className="optional-depth">
<summary>Go deeper: missing, null, zero, and schema changes</summary>

A missing field was not supplied. JSON null explicitly represents no value. Zero is a number. Treating all three as zero can turn an unknown measurement into a false observation. Our API rejects a missing or null note ID. The separate numeric field estimated_minutes allows zero; that is a supplied estimate, not a missing value.

A **schema version** identifies a data contract. A **source version**, such as notes-v1, identifies the authored note collection; changing its text should change that version. A **model version** identifies a predictor used by a model-based service. These are different: updating content or weights may leave the response shape unchanged. Renaming a required field can break clients even if the source stays the same. Document changes, test old consumers, and use an explicit migration or compatible transition.

</details>

## 4. Treat failure as part of the interface

A response includes a **status code**, headers, and sometimes a body. Status codes describe request handling, not model accuracy.

| Result | Meaning and useful next action |
|---|---|
| 200 | Request succeeded. Parse and validate the body before using it. |
| 400 | Bad request. Inspect the input and the endpoint's error message. |
| 401 / 403 | Missing or invalid authentication / access refused. Check credentials and permissions. |
| 404 | Resource or route not found. Check the URL and identifier. |
| 429 | Too many requests. Follow the service's limit policy and any Retry-After guidance. |
| 500 / 503 | Server error / service unavailable. A temporary problem is possible; investigate before retrying. |

A **timeout** means the client stopped waiting during an operation. It is not an HTTP status, and it does not prove the server did nothing. A **retry** sends another attempt. Retry only when the failure and operation make that appropriate; cap attempts, increase the delay between them (**backoff**), and add a small random variation (**jitter**) to avoid synchronized bursts. See [HTTP status meanings](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status) and [429 handling](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429).

<details className="optional-depth">
<summary>Go deeper: idempotency and duplicate work</summary>

An operation is **idempotent** when repeating the same request has the same intended server effect as doing it once. Responses and logs can still differ. POST is not automatically idempotent: retrying “create a report” may create or bill for two reports if the first response was lost.

An API may support an **idempotency key**: reuse a unique identifier for retries of one operation, according to that API's documented rules. Sending a made-up header does nothing unless the server implements it. Our lookup server creates no history records, but the client appends a database row each time it completes successfully. Running it twice creates two history rows. See [HTTP method semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).

</details>

## 5. Diagnose a request before changing the model

<ApiExplorer client:load />

Use the explorer to locate the failure: input, access, availability, transport, or response contract. A prompt change cannot repair an invalid credential. More training cannot fix a wrong endpoint. First find which boundary failed.

**Authentication** establishes an identity or credential; **authorization** decides what that identity may access. A service API key often grants access under an account. Keep provider secrets on the backend, outside browser code and version control. Load them from protected runtime configuration or a secret store; avoid printing them in logs. Our local lesson needs no credentials.

<details className="optional-depth">
<summary>Go deeper: waiting, async work, streaming, and CORS</summary>

In a **synchronous** call, the caller waits for completion. **Asynchronous** code can let other work proceed while waiting; it does not make the model's computation intrinsically faster. A long job may return a job ID so the client can check its status later.

**Streaming** delivers a response incrementally. Displaying early text is useful, but those chunks may be incomplete; wait for completion before treating them as a finished structured result.

**CORS** is a browser mechanism controlling whether a page can read responses from a different origin. An origin includes scheme, host, and port. A Python client is not subject to browser CORS checks. CORS is not authentication: it does not stop arbitrary non-browser clients calling an API. See [MDN's CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

</details>

## 6. Choose how to represent and store data

**Memory** holds working values while a process runs; stopping the process usually loses them. **Persistence** keeps data beyond that process, for example in a file or database.

| Form | A useful role | Limitation to remember |
|---|---|---|
| CSV | Flat rows for import or inspection | Types, missing values, and quoting need agreed rules |
| JSON | Nested API messages and configuration | Structure alone supplies neither a schema nor data quality |
| Relational database | Tables with queries, constraints, and transactions | Design the fields and relationships deliberately |
| Object storage | Files such as source PDFs, images, or dataset snapshots | Querying records usually needs another layer |

In a relational table, a **row** is a record and a **column** is a field. A **primary key** identifies a row. A **foreign key** references a key in another table, linking records. An **index** can accelerate particular lookups, at the cost of storage and write work.

An **API** describes how to interact; a **database** stores and queries data. They are not alternatives. A backend can expose an API while reading its database internally. Also, persisting a conversation does not train a model or ensure that the next request will include that conversation.

<details className="optional-depth">
<summary>Go deeper: relational, document, vector, and cache storage</summary>

A document database organizes records as documents, often with nested fields. A vector index supports similarity search over numeric representations called embeddings; we will build those in the search chapters. Some databases combine these capabilities. Similarity does not prove truth or grant access to a document.

A **cache** keeps reusable results to reduce repeated work. Its values can become stale, so decide when to refresh or invalidate them. Include relevant model, input, and access context in a cache design; a result for one user may be inappropriate for another.

</details>

## 7. Ask precise questions with SQL

**SQL** is a language for working with relational data. Suppose the starter has saved these note lookups (showing a subset of its columns):

| id | note_id | estimated_minutes | source_version |
|---|---|---|---|
| 1 | N03 | 10 | notes-v1 |
| 2 | N02 | 15 | notes-v1 |
| 3 | N01 | 20 | notes-v1 |

```sql
SELECT id, note_id, estimated_minutes
FROM note_history
WHERE estimated_minutes >= 15
ORDER BY id;
```

SELECT chooses columns, FROM names the table, WHERE filters rows, and ORDER BY specifies order. The result contains IDs **2 and 3**. Without ORDER BY, do not rely on the returned order. A **JOIN** combines matching rows from tables; an **aggregation**, such as AVG, summarizes a group. See the [SQLite SELECT reference](https://www.sqlite.org/lang_select.html).

When a value comes from a user, bind it separately instead of building SQL with string concatenation. In Python's sqlite3 API, <code>?</code> marks a value to bind:

```python
rows = connection.execute(
    "SELECT id FROM note_history WHERE estimated_minutes >= ? ORDER BY id",
    (15,),
).fetchall()
```

Here <code>connection</code> is an open database connection. <code>(15,)</code> is a one-item tuple, and <code>fetchall()</code> collects the result rows. This fragment assumes the table already exists; the starter provides the runnable setup.

<details className="optional-depth">
<summary>Go deeper: transactions and trustworthy records</summary>

A **transaction** groups database changes into a unit that commits or rolls back. It prevents a partially completed group of writes from being accepted as a completed change. It does not make an external API call and a database write one automatic transaction.

The starter commits one inserted row after validating the API response and closes its connection. If the API succeeds but saving fails, the client reports that failure. These rows record retrieved notes, not proof that you studied or mastered them. Actual study sessions and quiz results would require separately collected observations. See [Python's sqlite3 guide](https://docs.python.org/3/library/sqlite3.html).

</details>

## 8. Make the data path reproducible

A **data pipeline** is a sequence of steps that moves and transforms data. **ETL** means extract, transform, load; **ELT** loads before transformation. For a small study-note history, consider this path:

<SoftwareDiagrams kind="pipeline" />

Keep the original source available when appropriate, then check required fields, units, allowed ranges, missing values, and duplicates. Record what was rejected and why. Interpreting 20 minutes as 20 hours is a unit error that perfectly valid JSON will not catch. Removing duplicates requires a meaningful identity; two lookups of N01 may be separate events.

**Provenance** records where data came from and how it changed. For an AI result, keep enough context to reproduce or investigate it: an input reference, source and code versions, relevant settings, and timing; include model versions when a model is used. Log status and latency without needlessly copying sensitive inputs or credentials.

Use **Git** to version code and small configuration files; a **commit** is a recorded snapshot. Review changes with a diff. Keep secrets and generated databases out of commits. Record dataset versions separately when datasets are too large or unsuitable for the code repository. See [Git's version-control introduction](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control).

A **unit test** checks a small piece, such as response validation. An **integration test** checks cooperating pieces, such as sending an actual request to the service and reading its response. A **model evaluation** measures prediction quality on suitable examples. Passing software tests does not establish model quality.


In terminal B, make a request and inspect the saved result:

```powershell
py client.py N01
py inspect_data.py
```

The first command reports **Note: N01 | Overfitting | 20 minutes (notes-v1)** and saves a row in <code>study_history.db</code> beside client.py. A fresh database starts at row 1. The inspection script queries notes with estimated study time of at least 15 minutes, so it displays this row. Later successful client runs append records; inspection only reads them.

<SoftwareDiagrams kind="project" />

Follow these responsibilities in the code:

- **server.py** parses the request, validates the ID, looks it up in notes.json, and returns the authored note as JSON.
- **client.py** encodes the input, calls /notes/lookup with a timeout, validates the response, then inserts one SQLite row using bound values.
- **inspect_data.py** opens the existing database for reading and runs the filter query.

The client sets a five-second timeout on blocking network operations and makes one attempt. That setting is not a strict deadline for the entire program. Stop the server with **Ctrl+C**. If port 8765 is occupied, use <code>py server.py --port 8766</code> and <code>py client.py N01 --port 8766</code>.

<div className="callout"><strong>What this project establishes:</strong> two real Python programs communicate over local HTTP and store a checked result. Finding an exact note ID does not answer an arbitrary question, verify a source’s truth, or measure learning. Later chapters add semantic retrieval and generation. Python's built-in HTTP server is a learning tool here; it is bound to your computer's loopback address and is not a production deployment.</div>

<details className="optional-depth">
<summary>Read the request-building code</summary>

```python
import json
from urllib.request import Request, urlopen

body = json.dumps({"note_id": "N01"}).encode("utf-8")
request = Request(
    "http://127.0.0.1:8765/notes/lookup",
    data=body,
    headers={"Content-Type": "application/json"},
    method="POST",
)
with urlopen(request, timeout=5) as response:
    result = json.loads(response.read().decode("utf-8"))
print(result["title"])  # Overfitting
```

Run this only while the server is active. <code>Request</code> constructs the message; <code>urlopen</code> sends it. The <code>with</code> block closes the response when finished. This short fragment shows the mechanics; the downloadable client also checks the content type, status, and fields, reports failures, and persists successful results. See [urllib.request](https://docs.python.org/3/library/urllib.request.html) and the [HTTP server documentation](https://docs.python.org/3/library/http.server.html).

</details>
