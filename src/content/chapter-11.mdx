## 1. Start with a small product promise

“Help me choose a note about how models learn, estimated at no more than 30 minutes. Exclude notes I have completed. I prefer an introductory explanation.” This request gives us a task small enough to build and test.

The application returns one suggested note, the catalog facts that explain the choice, and exam timing if supplied. If nothing qualifies, it says so and lets the learner change the request. It never promises that the learner will benefit from the note.

An **acceptance criterion** is an observable condition for calling a feature successful. Here, the chosen note must exist in the catalog, match the required topic, have an estimate within the time limit, and be absent from the learner's completed list. A missing exam date must stay unknown. These conditions are more useful than “make the AI good.”

<ProjectDiagrams kind="pipeline" />

The first working version is a **baseline**: a simple reference implementation to compare improvements against. Our selection rules and template explanation need no trained model. Adding an LLM makes the explanation stage generative; it does not turn the ranking rule into learned personalization. This project connects Chapters 4–5's software foundations with Chapters 9–10's prompting and validation.

## 2. Keep catalog facts separate from preferences

The downloadable study pack has seven authored notes. Each record combines a stable ID, title, text, topic tags, level, study-time estimate, and optional exam metadata for that topic. N01, N02, and N03 retain Chapter 5’s titles, text, and estimates. For this compact project, timetable metadata is bundled with each note; a larger app would keep separately versioned timetable records. A **stable ID** identifies the same record even when its display title changes. For example:

```json
{
  "id": "N01",
  "title": "Overfitting",
  "topics": ["learning", "data"],
  "level": "introductory",
  "estimated_minutes": 20,
  "exam_date": null,
  "text": "A model can fit training examples too closely and perform poorly on new cases."
}
```

Preferences are a different object: `topic`, `max_minutes`, `prefer_introductory`, and `completed_ids`. The learner can change them without rewriting the note's study-time estimate. `null` means a value is unknown; it does not mean zero minutes or that no exam exists. A study estimate is planning metadata, not measured completion time. Marking a note completed is a learner input, not proof of mastery.

The catalog's `version` identifies this input snapshot. Recording it alongside the request helps explain why a result changed after an edit. The topic names are real; level labels, study estimates, and exam dates are authored teaching metadata. They are not current course or timetable information.

<details className="optional-depth"><summary>Go deeper: data validation is not factual verification</summary><p>The project rejects duplicate note IDs, unknown topic tags, unexpected fields, and invalid types. It accepts a null study-time estimate as missing data. These checks make records usable by the program; they do not prove that a real-world note actually has that study-time estimate. A real catalog also needs provenance, update dates, course-specific timetable information, and a process for correcting errors. We will develop data-quality concepts in Chapter 12.</p></details>

## 3. Filter hard constraints before ranking

A **hard constraint** must hold for a result to qualify. Our hard constraints are the required topic, maximum study-time estimate, and exclusion of completed notes. The “any” topic option removes only the topic restriction. “Maximum 30 minutes” includes a note estimated at exactly 30 minutes.

A **soft preference** helps choose among qualifying results. Here, an introductory level is preferred, not required. An advanced note can still be returned if it is the best eligible option under our policy.

<ProjectDiagrams kind="ranking" />

Overfitting passes the default request: it has the learning tag, is estimated at 20 minutes, and is not yet completed. Embeddings is estimated at 45 minutes and has only the search tag, so it fails two constraints. Backpropagation has a learning tag but no study-time estimate; the program cannot establish that it fits the time limit, so it is excluded too.

<details className="optional-depth"><summary>Go deeper: requirements should match the wording</summary><p>“I would prefer an introductory note” allows a tradeoff. “Only show introductory notes” expresses a hard constraint and would need a separate filter. Likewise, “under 30 minutes” strictly means less than 30, while this project's maximum-time control means at most 30. Translate wording into explicit rules before implementation. If an interface quietly changes the meaning, even perfectly executed code can solve the wrong problem.</p></details>

## 4. Rank candidates with a transparent rule

A **candidate** is a note still under consideration. **Ranking** puts candidates in a preferred order. Our small baseline assigns an eligible note one point if introductory level is preferred and the note is introductory; otherwise it gets zero. Higher scores come first.

| Eligible note for the default request | Introductory-level score | Study-time estimate |
| --- | --- | --- |
| Overfitting · N01 | 1 | 20 minutes |
| Train-validation splits · N04 | 1 | 25 minutes |
| Gradient descent · N02 | 0 | 15 minutes |

We break equal scores by shorter study-time estimate, then note ID. Overfitting wins over Train-validation splits because 20 is less than 25. Gradient descent follows both because its score is lower, even though it is shorter than Train-validation splits. This is a deliberate product policy, not a mathematical law about better notes.

The score is neither a probability nor a predicted rating. We have not trained anything or used other learners' behavior. Large recommenders often separate candidate generation, scoring, and re-ranking; this project's filter-and-sort pipeline is a small, explicit design. See [Google's recommendation architecture overview](https://developers.google.com/machine-learning/recommendation/overview/types).

<details className="optional-depth"><summary>Go deeper: cold start, ties, and learning later</summary><p><strong>Cold start</strong> means making recommendations with little interaction history for a new learner or item. Asking for preferences is one starting point. Later, ratings, quiz performance, or item features could support learned scoring, but you would need suitable data and evaluation. Even a learned score often needs explicit tie-breaks and product constraints. Stable sorting rules make this baseline reproducible; they do not make it personalized beyond the supplied preferences.</p></details>

## 6. Run and understand the Python project

<a className="download-link" href="/downloads/chapter-11-learning-project.zip" download>Download the study suggestion project ZIP ↗</a>

Extract all files into one folder and open a terminal there. Python 3.10 or newer is sufficient; no third-party packages are needed for this workbook.

```powershell
py study_app.py
py evaluate.py
py -m unittest -v test_study_app.py
```

Use your working `python` or `python3` command if `py` is unavailable. The first command prints a result with `status: ok`, note ID N01, and an unknown exam date. The other commands run the prepared evaluation and code tests. None calls a model service.

Open `preferences.json` and put `"N01"` in `completed_ids`; rerun the first command. The recommendation should change to N04. Set `prefer_introductory` to `false`; it should change to N02. These are the same decisions you explored in the browser.

The main `recommend` function validates inputs, creates an exclusion-reason list for each record, sorts eligible notes, and builds a result. Its sorting key is compact:

```python
eligible.sort(key=lambda m: (
    -int(p["prefer_introductory"] and m["level"] == "introductory"),
    m["estimated_minutes"],
    m["id"],
))
```

Python compares tuple elements from left to right. Negating the score puts one-point notes before zero-point notes in an ascending sort. Study-time estimate and ID resolve ties. Missing study-time estimates have already been filtered out.

## 7. Add an LLM explanation as a separate stage

An LLM can phrase the explanation more flexibly. It should receive the learner preferences and the selected note's facts, rather than being asked to invent an entire catalog. In this project, S1 holds preferences, S2 holds the selected note, and S3 holds its supplied timetable information. N01 is a note ID; S2 is a source ID within the current prompt.

First exercise the integration offline:

```powershell
py study_app.py --draft template
py study_app.py --draft unsupported
```

The template mode constructs an authored response and sends it through Chapter 10's real envelope, JSON, field, and source-ID checks. It is not generated by an LLM. Unsupported mode deliberately inserts an unsupported 2026-12-01 exam date; it demonstrates that a false fact can pass structural checks.

The result keeps two separate objects. `recommendation` is the catalog-based card. `draft.candidate` contains the optional prose and the familiar four Chapter 10 fields. Its `review_required` status means a person must compare claims with the supplied records. The draft never overwrites the card's note or exam-date field. Valid structure still allows factual mistakes, as described in [OpenAI's Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs).

This transmits the selected records and preferences and can incur API charges. Keep credentials outside the handbook browser and source files. The download README explains setup and limitations; no live API call was made for this edition.</p><p>The project makes at most one provider call for a requested draft and none when no note qualifies. Separating the draft limits its ability to corrupt catalog fields, but does not make its prose trustworthy. Prompt instructions alone are not evidence verification.</p></details>

## 8. Make unhelpful outcomes understandable

An empty result is sometimes the correct answer. With learning and a 10-minute maximum, “No matching note” respects the learner's request. Quietly increasing the limit would conceal a product decision the learner did not make.

| Situation | Project behavior |
| --- | --- |
| Invalid preference types or unknown IDs | Stop and describe the input problem |
| Valid request, no eligible note | Return `no_match`; suggest changing preferences |
| Exam date missing | Keep `null`; show “unknown in this catalog” |
| Optional provider fails | Keep the catalog-based card; record the draft failure |
| Draft passes structure checks | Keep it separate with `review_required` |

Keeping a usable simpler result when an optional service fails is **graceful degradation**. The interface must distinguish that result from a successful model response. In the CLI, a normal result or no match exits 0; a requested draft failure exits 1; invalid input or setup exits 2. A successful exit code describes program behavior, not factual correctness of model prose.

## 9. Evaluate the product, not just the happy path

The workbook's `eval_cases.json` contains 12 requests and expected note IDs, including expected no-match results. These expectations were written for the stated policy; the recommender does not generate its own answer key. Running `evaluate.py` compares actual IDs with that file and reports each case.

The default catalog passes all 12 cases. That means **12 prepared policy checks passed**, not “100% recommendation accuracy.” Cases cover exact time boundaries, completion exclusions, soft-preference changes, topic tags, and empty results. They do not measure whether learners improve after studying the selected notes or whether a live LLM writes accurate explanations.

<ProjectDiagrams kind="evaluation" />

Code tests add different checks: every eligible note respects the constraints across many time limits; duplicate IDs fail; missing study-time estimates are excluded; ties are stable; provider failures preserve the card; and no-match requests make zero provider calls. The tests use Python's standard [unittest framework](https://docs.python.org/3/library/unittest.html).

<details className="optional-depth"><summary>Go deeper: evaluating an improvement fairly</summary><p>To compare an LLM explanation with the template, keep the same requests and catalog. Check factual support, correct handling of missing data, clarity, latency, and cost; collect learner feedback for usefulness. Count unsupported claims separately from valid-JSON rates. A nicer sentence is not an improvement if it invents an exam date. These prepared cases are development checks. If you tune prompts or a learned ranker against them, preserve separate unseen evaluation cases for a less biased final assessment. Real timetables can change by course and term.</p></details>

## 12. Keep the boundaries visible

<blockquote>Validate the inputs. Filter required constraints. Rank eligible choices. Explain from supplied facts. Review model prose separately. Test the cases where the answer is missing or the service fails.</blockquote>

This is the first stage of the personal learning assistant. Note search, source-backed answers, quizzes, prerequisite checks, and revision scheduling are later extensions. The current project checks supplied preferences and estimates; it does not enforce prerequisites or infer weak topics.

You have completed a small product with an inspectable policy, a working interface, a Python implementation, and repeatable checks. You can now explain which behavior comes from data, which comes from application rules, and where an optional model enters the system.
