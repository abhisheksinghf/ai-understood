## 1. Start with a small product promise

“Help me choose an unseen adventure movie that fits into 120 minutes. I would prefer something light.” This request gives us a task small enough to build and test.

The application returns one suggested movie, the catalog facts that explain the choice, and streaming availability if supplied. If nothing qualifies, it says so and lets the viewer change the request. It never promises that the viewer will enjoy the film.

An **acceptance criterion** is an observable condition for calling a feature successful. Here, the chosen movie must exist in the catalog, match the required genre, fit the time limit, and be absent from the viewer's seen list. A missing streaming service must stay unknown. These conditions are more useful than “make the AI good.”

<ProjectDiagrams kind="pipeline" />

The first working version is a **baseline**: a simple reference implementation to compare improvements against. Our selection rules and template explanation need no trained model. Adding an LLM makes the explanation stage generative; it does not turn the ranking rule into learned personalization. This project connects Chapters 4–5's software foundations with Chapters 9–10's prompting and validation.

## 2. Keep catalog facts separate from preferences

The downloadable catalog has seven fictional movies. Each has a stable ID, title, genre tags, tone, runtime, and an optional streaming service. A **stable ID** identifies the same record even when its display title changes. For example:

```json
{
  "id": "M001",
  "title": "Moonlight Map",
  "genres": ["adventure", "comedy"],
  "tone": "light",
  "runtime_minutes": 105,
  "streaming_service": null
}
```

Preferences are a different object: `genre`, `max_minutes`, `prefer_light`, and `seen_ids`. The viewer can change them without rewriting the movie's runtime. `null` means a value is unknown; it does not mean zero minutes or unavailable everywhere.

The catalog's `version` identifies this input snapshot. Recording it alongside the request helps explain why a result changed after an edit. All movie titles, tone labels, and service names in this project are invented for learning. They are not current cinema or streaming information.

<details className="optional-depth"><summary>Go deeper: data validation is not factual verification</summary><p>The project rejects duplicate movie IDs, unknown genre tags, unexpected fields, and invalid types. It accepts a null runtime as missing data. These checks make records usable by the program; they do not prove that a real-world film actually has that runtime. A real catalog also needs provenance, update dates, regional availability, and a process for correcting errors. We will develop data-quality concepts in Chapter 12.</p></details>

## 3. Filter hard constraints before ranking

A **hard constraint** must hold for a result to qualify. Our hard constraints are the required genre, maximum runtime, and exclusion of seen movies. The “any” genre option removes only the genre restriction. “Maximum 120 minutes” includes a film that lasts exactly 120 minutes.

A **soft preference** helps choose among qualifying results. Here, a light tone is preferred, not required. A serious movie can still be returned if it is the best eligible option under our policy.

<ProjectDiagrams kind="ranking" />

Moonlight Map passes the default request: it has the adventure tag, lasts 105 minutes, and is unseen. City Sprint lasts 140 minutes and has only the action tag, so it fails two constraints. Unlisted Voyage has an adventure tag but no runtime; the program cannot establish that it fits the time limit, so it is excluded too.

<details className="optional-depth"><summary>Go deeper: requirements should match the wording</summary><p>“I would prefer something light” allows a tradeoff. “Only show light movies” expresses a hard constraint and would need a separate filter. Likewise, “under 120 minutes” strictly means less than 120, while this project's maximum-length control means at most 120. Translate wording into explicit rules before implementation. If an interface quietly changes the meaning, even perfectly executed code can solve the wrong problem.</p></details>

## 4. Rank candidates with a transparent rule

A **candidate** is a movie still under consideration. **Ranking** puts candidates in a preferred order. Our small baseline assigns an eligible movie one point if light tone is preferred and the movie is light; otherwise it gets zero. Higher scores come first.

| Eligible movie for the default request | Light-tone score | Runtime |
| --- | --- | --- |
| Moonlight Map · M001 | 1 | 105 minutes |
| Forest Signal · M003 | 1 | 115 minutes |
| Quiet Orbit · M004 | 0 | 110 minutes |

We break equal scores by shorter runtime, then movie ID. Moonlight Map wins over Forest Signal because 105 is less than 115. Quiet Orbit follows both because its score is lower, even though it is shorter than Forest Signal. This is a deliberate product policy, not a mathematical law about better movies.

The score is neither a probability nor a predicted rating. We have not trained anything or used other viewers' behavior. Large recommenders often separate candidate generation, scoring, and re-ranking; this project's filter-and-sort pipeline is a small, explicit design. See [Google's recommendation architecture overview](https://developers.google.com/machine-learning/recommendation/overview/types).

<details className="optional-depth"><summary>Go deeper: cold start, ties, and learning later</summary><p><strong>Cold start</strong> means making recommendations with little interaction history for a new viewer or item. Asking for preferences is one starting point. Later, ratings, watch behavior, or item features could support learned scoring, but you would need suitable data and evaluation. Even a learned score often needs explicit tie-breaks and product constraints. Stable sorting rules make this baseline reproducible; they do not make it personalized beyond the supplied preferences.</p></details>

## 6. Run and understand the Python project

Extract all files into one folder and open a terminal there. Python 3.10 or newer is sufficient; no third-party packages are needed for this workbook.

```powershell
py movie_app.py
py evaluate.py
py -m unittest -v test_movie_app.py
```

Use your working `python` or `python3` command if `py` is unavailable. The first command prints a result with `status: ok`, movie ID M001, and an unknown streaming service. The other commands run the prepared evaluation and code tests. None calls a model service.

Open `preferences.json` and put `"M001"` in `seen_ids`; rerun the first command. The recommendation should change to M003. Set `prefer_light` to `false`; it should change to M004. These are the same decisions you explored in the browser.

The main `recommend` function validates inputs, creates an exclusion-reason list for each record, sorts eligible movies, and builds a result. Its sorting key is compact:

```python
eligible.sort(key=lambda m: (
    -int(p["prefer_light"] and m["tone"] == "light"),
    m["runtime_minutes"],
    m["id"],
))
```

Python compares tuple elements from left to right. Negating the score puts one-point movies before zero-point movies in an ascending sort. Runtime and ID resolve ties. Missing runtimes have already been filtered out.

## 7. Add an LLM explanation as a separate stage

An LLM can phrase the explanation more flexibly. It should receive the viewer preferences and the selected movie's facts, rather than being asked to invent an entire catalog. In this project, S1 holds preferences, S2 holds the selected movie, and S3 holds its supplied streaming information. M001 is a movie ID; S2 is a source ID within the current prompt.

First exercise the integration offline:

```powershell
py movie_app.py --draft template
py movie_app.py --draft unsupported
```

The template mode constructs an authored response and sends it through Chapter 10's real envelope, JSON, field, and source-ID checks. It is not generated by an LLM. Unsupported mode deliberately inserts an ExampleFlix claim; it demonstrates that a false fact can pass structural checks.

The result keeps two separate objects. `recommendation` is the catalog-based card. `draft.candidate` contains the optional prose and the familiar four Chapter 10 fields. Its `review_required` status means a person must compare claims with the supplied records. The draft never overwrites the card's movie or streaming-service field. Valid structure still allows factual mistakes, as described in [OpenAI's Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs).

<details className="optional-depth"><summary>Go deeper: optional live mode and the review boundary</summary><p>With the local credentials and compatible model configuration described in Chapter 10, explicitly run `py movie_app.py --draft live`. This transmits the selected records and preferences and can incur API charges. Keep credentials outside the handbook browser and source files. The download README explains setup and limitations; no live API call was made for this edition.</p><p>The project makes at most one provider call for a requested draft and none when no movie qualifies. The browser demo remains offline. Check the draft's selected title, runtime, preference claims, source support, and availability before using its wording. Separating the draft limits its ability to corrupt catalog fields, but does not make its prose trustworthy. Prompt instructions alone are not evidence verification.</p></details>

## 8. Make unhelpful outcomes understandable

An empty result is sometimes the correct answer. With adventure and a 90-minute maximum, “No matching movie” respects the viewer's request. Quietly increasing the limit would conceal a product decision the viewer did not make.

| Situation | Project behavior |
| --- | --- |
| Invalid preference types or unknown IDs | Stop and describe the input problem |
| Valid request, no eligible movie | Return `no_match`; suggest changing preferences |
| Streaming service missing | Keep `null`; show “unknown in this catalog” |
| Optional provider fails | Keep the catalog-based card; record the draft failure |
| Draft passes structure checks | Keep it separate with `review_required` |

Keeping a usable simpler result when an optional service fails is **graceful degradation**. The interface must distinguish that result from a successful model response. In the CLI, a normal result or no match exits 0; a requested draft failure exits 1; invalid input or setup exits 2. A successful exit code describes program behavior, not factual correctness of model prose.

## 9. Evaluate the product, not just the happy path

The workbook's `eval_cases.json` contains 12 requests and expected movie IDs, including expected no-match results. These expectations were written for the stated policy; the recommender does not generate its own answer key. Running `evaluate.py` compares actual IDs with that file and reports each case.

The default catalog passes all 12 cases. That means **12 prepared policy checks passed**, not “100% recommendation accuracy.” Cases cover exact time boundaries, seen exclusions, soft-preference changes, genre tags, and empty results. They do not measure whether viewers enjoy the recommendations or whether a live LLM writes accurate explanations.

<ProjectDiagrams kind="evaluation" />

Code tests add different checks: every eligible movie respects the constraints across many time limits; duplicate IDs fail; missing runtimes are excluded; ties are stable; provider failures preserve the card; and no-match requests make zero provider calls. The tests use Python's standard [unittest framework](https://docs.python.org/3/library/unittest.html).

<details className="optional-depth"><summary>Go deeper: evaluating an improvement fairly</summary><p>To compare an LLM explanation with the template, keep the same requests and catalog. Check factual support, correct handling of missing data, clarity, latency, and cost; collect viewer feedback for usefulness. Count unsupported claims separately from valid-JSON rates. A nicer sentence is not an improvement if it invents a service. These prepared cases are development checks. If you tune prompts or a learned ranker against them, preserve separate unseen cases for a less biased final assessment. Real availability also changes by date and region.</p></details>
