## 1. Define the behavior you want to teach

Start with an observable target: “Use the supplied movie evidence, respect constraints, and state when availability is unknown.” “Make the model smarter” is too vague to turn into labels or an evaluation.

Separate **domain adaptation** from **instruction adaptation**. Continuing language-model training on domain text can teach its vocabulary and patterns; supervised instruction examples teach how to respond to tasks. Neither guarantees reliable recall of an exact changing catalog. Keep retrieval and live tools when the application needs them.

Choose a suitable base checkpoint and record a prompt baseline. Define success cases, difficult cases, and behaviors you must preserve. The same training method can help one task and harm another, so a lower training loss is only one signal.

## 2. Build demonstrations that match real requests

In **supervised fine-tuning (SFT)**, each example provides an input and a desired output. A movie example should contain the evidence available at deployment, not hidden facts the model will never receive.

```text
Input: Recommend a calm film under 100 minutes.
Evidence: M001, Moonlight Map, 94 minutes, gentle pacing.
Streaming availability: not supplied.
Target: Moonlight Map fits the runtime limit and calm mood.
        I cannot establish streaming availability from this card.
```

Include realistic variety: no matches, conflicting constraints, missing evidence, alternate wording, and valid tool failures. Review targets for unsupported claims and consistent formatting. A hundred near-duplicates do not provide the coverage of a hundred meaningfully different requests.

Split data before expanding it with paraphrases. Keep related conversations or movie examples together when needed to avoid leakage. Use a training set for updates, a validation set for choices such as stopping, and a final test set reserved for assessment. Check permission to use the data and remove secrets or unnecessary personal information.

## 3. Understand what SFT optimizes

For an autoregressive model, SFT usually increases the probability of target tokens given the prompt and preceding target tokens. This use of the known target prefix is **teacher forcing**. A common assistant-only objective masks prompt tokens out of the loss:

$$L_{SFT}=-\frac{1}{\sum_t m_t}\sum_t m_t\log p_\theta(y_t\mid x,y_{<t}).$$

$x$ is the prompt and evidence, $y_t$ a target token, and $m_t$ is 1 for positions included in the objective and 0 otherwise. The denominator counts included tokens; an example with none should be rejected. Training then uses backpropagation and an optimizer to update the selected parameters.

**A loss mask is not an attention mask.** Masking the user's words out of the loss does not hide them from the assistant. They remain context for predicting its answer. Some recipes train on more tokens; inspect your configuration rather than assuming one universal default. See the [SFT trainer documentation](https://huggingface.co/docs/trl/en/sft_trainer) for supported loss and dataset choices.

If a target token has probability 0.25, its negative log-likelihood is about 1.3863 nats. Raising that probability to 0.5 reduces the contribution to 0.6931. This rewards matching the target, even when the target itself contains a factual error.

## 4. Choose which parameters can change

**Full fine-tuning** updates the base model's weights. **Parameter-efficient fine-tuning (PEFT)** trains a smaller parameter set. These describe parameter choices, while SFT and preference losses describe training objectives; they can be combined.

One PEFT method, [LoRA](https://arxiv.org/abs/2106.09685), keeps a base weight matrix frozen and learns a low-rank addition. For a column vector $x$:

$$h=W_0x+\frac{\alpha}{r}BAx.$$

If $W_0$ has shape $d_{out}\times d_{in}$, then $A$ is $r\times d_{in}$ and $B$ is $d_{out}\times r$. Their product fits the original layer's shape but has rank at most $r$. Rank $r$ controls capacity; $\alpha$ controls the update scale. Here we use conventional $\alpha/r$ scaling; other variants exist.

<TuningDiagrams kind="lora" />

A 4096 × 4096 matrix has **16,777,216** weights. Rank 8 uses **65,536** adapter parameters, about 0.39% of that count. This compares trainable parameters for one layer, excluding biases and other components. The frozen base still exists and participates in computation.

<details className="optional-depth">
<summary>Go deeper: initialization, rank, and target modules</summary>

A common initialization makes one factor nonzero and the other zero, giving a zero initial update. In the lab, A is nonzero and B is zero. B can receive a gradient immediately; A can begin changing after B becomes nonzero. If both factors start at zero, the simple product branch gives zero gradients to both.

Increasing rank increases the update's representational capacity and parameter count. It does not guarantee higher quality. Which layers receive adapters also matters: attention projections and feed-forward projections can affect behavior differently.

For a compatible unquantized linear layer, adding the scaled product to the base matrix can merge the adapter for inference. Preserve the original artifacts and verify the merged model. Quantized merging may involve conversion and rounding, so do not assume bitwise-identical results.

</details>

## 5. Separate quantized storage from learning

**QLoRA** adapts a model through LoRA while keeping the pretrained base frozen in a quantized representation. Gradients flow through computation using that base into the adapters. The [QLoRA paper](https://arxiv.org/abs/2305.14314) combines a 4-bit NormalFloat format, quantized quantization constants, and paged optimizers to reduce memory demands.

It does not mean every multiplication, gradient, activation, and optimizer value is four bits. Storage precision and computation precision differ. Training also needs activations and optimizer state, so the inference memory estimate from Chapter 26 is not a training budget.

| Choice | What mainly changes | What remains to verify |
| --- | --- | --- |
| Full fine-tuning | Many base parameters | Training memory, regressions, cost |
| LoRA | Selected low-rank adapter parameters | Rank, target layers, task quality |
| QLoRA | Adapters around a quantized frozen base | Runtime support, memory peaks, numerical effects |

Use validation to choose learning rate, training duration, and adapter settings. Too many epochs can memorize the demonstrations; too few can leave the behavior unchanged. Gradient accumulation combines gradients across microbatches before an optimizer step, allowing a larger effective batch under a memory limit.

## 6. Turn judgments into preference data

A preference example contains **the same prompt**, two responses, and a judgment about which is better under a rubric. It tells the learner about relative quality, not necessarily the single ideal wording.

For the movie card above, compare:

| Response | Judgment under an evidence-based rubric |
| --- | --- |
| A: “Moonlight Map fits your limit and calm mood. Availability is not supplied.” | Preferred: supported and honest about missing evidence |
| B: “Guaranteed to be your favorite, streaming on every service tonight!” | Rejected: unsupported certainty and availability claims |

Specify what matters: factual support, constraint satisfaction, useful explanation, and suitable length. Collect disagreements and allow ties or invalid pairs during annotation; do not force every ambiguous pair into a confident label. Filter or handle them deliberately in the training recipe.

Human labels are not automatically consistent, and model-generated labels are not independent truth. If judges reward confidence or verbosity over support, optimization can amplify those traits. Preference learning shapes an assistant's response behavior; it is not automatically a recommender trained on each viewer's movie ratings.

<details className="optional-depth">
<summary>Go deeper: preference bias and useful negative examples</summary>

Compare replies with the same available evidence. Otherwise, a label can accidentally favor access to additional facts instead of a better response policy. Blind candidate identities and vary their presentation order when collecting judgments.

Easy pairs of excellent versus nonsensical answers may not teach subtle distinctions. Include plausible mistakes such as violating a runtime limit or inventing a platform. Avoid making every rejected answer longer: the learner may discover length as a shortcut.

Record the rubric, annotator or judge provenance, and uncertain cases. Separate disagreements about taste from errors such as contradicted facts. If a judge is another model, audit its outputs against evidence and human review; shared biases can survive a large synthetic dataset.

</details>

## 7. Learn a reward model, then optimize a policy

A common **reinforcement learning from human feedback (RLHF)** workflow begins with SFT, learns a reward model from preference comparisons, then optimizes the response-generating model, called the **policy**. The [InstructGPT paper](https://arxiv.org/abs/2203.02155) illustrates this sequence.

A pairwise reward model assigns scores $r(x,y)$. A common comparison model is:

$$P(y^+\succ y^-\mid x)=\sigma\big(r(x,y^+)-r(x,y^-)\big).$$

The sigmoid turns a score difference into a modeled preference probability. Reward scores are learned proxies, not truth scores. The policy generates responses; the reward model scores them; an RL algorithm such as Proximal Policy Optimization (PPO) updates the policy. A reference-policy penalty often discourages excessive drift.

**Reward hacking** occurs when optimization finds ways to score well without fulfilling the intended goal. Our movie assistant could learn confident praise because the scorer likes it. Evaluate evidence support, constraints, and regressions independently from reward.

<TuningDiagrams kind="preferences" />

<details className="optional-depth">
<summary>Go deeper: KL regularization and online versus offline learning</summary>

A simplified regularized objective maximizes expected reward minus $\beta D_{KL}(\pi_\theta\Vert\pi_{ref})$. KL measures how much the policy's distribution differs from a fixed reference under the evaluated prompts. It is not a distance to truth or a safety certificate.

In an online RL loop, the changing policy generates new responses used for updates. In standard offline DPO, training uses a fixed dataset of response pairs. Iterative approaches can collect new pairs between training rounds; the distinctions concern data collection and the objective, not just names.

PPO constrains policy updates using its own optimization machinery; reference regularization addresses drift from a reference. They are related controls but not interchangeable guarantees. Detailed RL algorithms return later in the handbook.

</details>

## 8. Optimize preferences directly with DPO

**Direct Preference Optimization (DPO)** trains a policy on chosen/rejected pairs relative to a fixed reference, without fitting a separate reward model in the standard recipe. It is still gradient-based training. See the [DPO paper](https://arxiv.org/abs/2305.18290) and [trainer's loss explanation](https://huggingface.co/docs/trl/en/dpo_trainer).

Let $\ell_\theta^+=\log\pi_\theta(y^+\mid x)$ and $\ell_\theta^-=\log\pi_\theta(y^-\mid x)$, with corresponding reference log-probabilities. With positive scaling coefficient $\beta$, define:

$$m=(\ell_\theta^+-\ell_\theta^-)-(\ell_{ref}^+-\ell_{ref}^-),\qquad L_{DPO}=-\log\sigma(\beta m).$$

The margin measures how much more the policy favors the chosen response over the rejected one **relative to the reference**. Positive margin lowers the pair loss. If policy and reference are identical, the margin is zero and loss is $\log 2\approx0.6931$, even if both strongly favor one response already.

For a language model, a completion's log-probability is the sum of its token log-probabilities conditioned on the prompt and preceding completion tokens. Standard DPO compares those completion scores, not a softmax over two displayed sentences. Our lab deliberately reduces the entire output space to two replies so the update can be inspected.

<details className="optional-depth">
<summary>Go deeper: beta, relative likelihood, and a scalar gradient</summary>

In DPO's regularized derivation, beta controls a reward-versus-reference tradeoff. In the pair loss, it also scales the margin and gradient. A larger beta is not simply a promise that a short training run will move farther or less far; data, learning rate, and optimization duration interact.

In the lab, $P(A)=\sigma(\theta)$ and $P(B)=1-P(A)$, so their log-odds equal $\theta$. For A preferred, $m=\theta-\theta_{ref}$ and:

$$\frac{\partial L}{\partial\theta}=-\beta\sigma(-\beta m),\qquad \theta_{new}=\theta-\eta\frac{\partial L}{\partial\theta}.$$

Starting at $\theta=\theta_{ref}=0$, with $\beta=0.5$ and learning rate $\eta=0.5$, the gradient is −0.25. One update gives $\theta=0.125$ and $P(A)\approx0.5312$.

A real vocabulary has many possible continuations. Improving a relative preference does not require both an absolute increase in the chosen response's probability and a decrease in the rejected response's probability. That simple complementary relationship is a special property of our two-outcome lab.

</details>

## 9. Evaluate the behavior and preserve the deployment recipe

Compare the adapted model with the baseline using unseen prompts and the same evidence and tools where possible. Measure factual support, hard constraints, useful style, appropriate uncertainty, and tool-call validity. Use blinded human comparisons or audited judges for subjective quality; record ties and sample counts.

Watch for **overfitting** to demonstrations and **catastrophic forgetting**, where adapting to one distribution harms previous capabilities. Evaluate general tasks as well as the new movie behavior. Falling training loss alongside worsening validation results is a reason to investigate, not to train longer automatically.

Save the base-model identity, tokenizer/chat template, data version, training configuration, adapter or checkpoint, and evaluation report. A LoRA adapter depends on a compatible base architecture and weights. Test the actual deployment artifact, including any merge or quantization, with the intended prompt and generation settings. Keep a tested rollback version.

Training does not grant tool permissions or keep availability current. Continue enforcing access, exact rules, and action validation in the application. A preferred answer can still be wrong; an adapted assistant still needs evidence.

## 12. Connect adaptation to broader generative AI

You can now distinguish the target used for learning, the parameters that change, and the evaluation needed afterward. SFT, LoRA, quantization, and preference optimization are different choices that can appear together in a training recipe.
