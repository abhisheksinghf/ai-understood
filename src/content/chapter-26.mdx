## 1. Decide what efficient means

Efficiency needs a workload and a quality target. A movie assistant serving interactive chat has different priorities from a nightly job summarizing thousands of reviews. Measure useful completed work, not just the fastest isolated operation.

| Measure | What it tells you | Movie-assistant example |
| --- | --- | --- |
| Time to first token (TTFT) | Delay before the response starts | How long the user waits for the opening words |
| Time between output tokens | How quickly streaming continues | Whether the explanation arrives smoothly |
| End-to-end latency | Time until the answer finishes | Includes queueing, retrieval, and generation |
| Throughput | Work completed per unit time | Requests or output tokens served per second |
| Peak memory and cost | Resources needed at the chosen load | Whether concurrent requests fit economically |

Report prompt/output lengths, concurrency, hardware, and model settings alongside results. A higher throughput can come with worse per-user latency. Check slower requests too: **p95 latency** is the value at or below which roughly 95% of measured request latencies fall.

<details className="optional-depth">
<summary>Go deeper: arithmetic is only part of the cost</summary>

An accelerator must move data as well as multiply numbers. A **compute-bound** workload is mainly limited by arithmetic capacity; a **memory-bandwidth-bound** workload is mainly limited by how fast data reaches that computation. Prefill has many known prompt positions to process together. Small-batch decoding often spends substantial time reading weights for relatively little work per step. These are tendencies, not rules for every model and device.

**FLOPs** count floating-point operations; **FLOP/s** is a rate. Fewer theoretical operations do not guarantee lower wall-clock latency if communication, conversion, or scheduling becomes the bottleneck. Benchmark the whole path with warmup, realistic lengths and load, and synchronized timing where the runtime executes device work asynchronously.

</details>

## 2. Count more than the model weights

The ideal weight payload is:

$$M_{weights}=P\frac{b_w}{8}\quad\text{bytes}.$$

$P$ is parameter count and $b_w$ is bits stored per parameter. Seven billion parameters at 16 bits require **14 billion bytes**, or **13.0385 GiB**. A GB is $10^9$ bytes; a GiB is $2^{30}$ bytes. Use consistent units when comparing estimates with available memory.

Inference also needs cache state, activations, temporary workspaces, and runtime allocations. Quantized formats can add scales, zero points, padding, or higher-precision tensors. A weight-file size alone cannot establish whether the application fits.

<EfficiencyDiagrams kind="memory" />

For a conventional full-context transformer cache with equally long sequences:

$$M_{KV}=2BTLH_{KV}d_h\frac{b_c}{8}\quad\text{bytes}.$$

$B$ is concurrent sequences, $T$ is retained tokens per sequence, $L$ is layers, $H_{KV}$ is KV heads, $d_h$ is head width, and $b_c$ is cache bits per value. The factor 2 counts **both keys and values**. Distinct sequences share the model's weights, but ordinarily need their own cache entries.

With $B=1$, $T=4096$, $L=32$, $H_{KV}=8$, $d_h=128$, and $b_c=16$, the cache is **0.5 GiB**. Four such sequences need 2 GiB. Include room for generated tokens, not only the initial prompt. The formula assumes no prefix sharing, eviction, beam expansion, or cache compression beyond the specified precision.

## 3. Reduce cache cost with the right architecture

Chapter 24 introduced multi-head attention. In ordinary **multi-head attention (MHA)**, each query head has its own key and value head. **Grouped-query attention (GQA)** lets several query heads share a KV head. **Multi-query attention (MQA)** shares one KV head across all query heads. Queries still form their own attention scores and mixtures. The [GQA paper](https://arxiv.org/abs/2305.13245) explains this architectural tradeoff.

<EfficiencyDiagrams kind="heads" />

In the previous memory example, switching the hypothetical KV-head count from 32 to 8 to 1 changes cache payload from **2 GiB → 0.5 GiB → 0.0625 GiB**. It does not establish equal answer quality or an identical runtime speedup. Deleting heads from a checkpoint is not a valid general conversion; use a compatible trained architecture or a tested adaptation method.

<details className="optional-depth">
<summary>Go deeper: long context, sliding windows, and useful evidence</summary>

With a full cache, retained length grows cache storage linearly. A new decoded query attends over that retained prefix. Dense prefill attention considers quadratically many position pairs, while the attention part of one new-token decode grows linearly with the retained length at fixed width.

**Sliding-window attention** limits the positions available to a layer and can bound that layer's retained cache. Some architectures mix local and global layers; their cache accounting must reflect both. Evicting tokens changes available context unless another mechanism preserves their information. Merely discarding old keys from a full-attention model is not an equivalent computation.

A supported long context window also does not prove reliable use of every detail. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) demonstrated sensitivity to where relevant information appears. Test your model with movie constraints placed throughout realistic inputs. Retrieval and concise context selection can still help when a larger window is available.

</details>

## 4. Store numbers with fewer bits

**Quantization** represents numerical values with a smaller set of values, reducing storage and sometimes computation or memory traffic. Weights, activations, and KV cache can use different precisions. A “4-bit model” does not automatically mean every operation and every tensor uses four bits. The [quantization concepts guide](https://huggingface.co/docs/transformers/main/en/quantization/concept_guide) describes these distinctions.

Our teaching quantizer uses symmetric integer codes. For $b$ bits, set $Q=2^{b-1}-1$ and choose scale $s=\max|w|/Q$ for a group:

$$q=\operatorname{clip}(\operatorname{round}(w/s),-Q,Q),\qquad \hat w=sq.$$

For 4 bits and maximum magnitude 1, $Q=7$ and $s=1/7$. A weight 0.43 becomes code 3 and reconstructs as **0.4286**. This scheme uses codes −7 through 7, leaving −8 unused. The lost detail is rounding error; reconstruction does not recover the original value exactly.

One scale for many weights is cheap, but an outlier can make small values round poorly. Smaller groups add scales and can reduce error. Our six weights take an ideal 3 bytes of 4-bit codes; adding one 4-byte scale gives **7 bytes**, while three pair scales give **15 bytes**. Metadata matters, especially in tiny groups.

<details className="optional-depth">
<summary>Go deeper: calibration, PTQ, and quantization-aware training</summary>

**Post-training quantization (PTQ)** compresses an already trained model. Some methods use representative calibration examples to choose how to preserve important computations. [GPTQ](https://arxiv.org/abs/2210.17323) is an example of a more sophisticated weight-quantization method than independent rounding. Our workbook does not implement GPTQ.

**Quantization-aware training (QAT)** exposes training to simulated quantization effects so parameters can adapt. Integer quantization may use a scale and a zero point; low-bit floating-point formats use different representations. Storage precision, multiplication precision, and accumulation precision need not match.

Measure task quality and speed after conversion. Supporting a numeric format is not the same as having a fast kernel for your workload. Dequantization, unsupported operations, or transfer overhead can offset savings. Lower average weight error is useful diagnostic information, not a guarantee of a better recommendation.

</details>

## 5. Make attention move less data

Naive dense attention can materialize a large matrix of scores between query and key positions. **FlashAttention** tiles the computation and manages intermediate results so it avoids writing the full attention matrix to high-bandwidth memory. It calculates the same attention operation up to numerical differences, while reducing expensive memory traffic. See the [FlashAttention paper](https://arxiv.org/abs/2205.14135).

It does not remove the dense pairwise interactions: doubling sequence length still quadruples their count at fixed head count. **Sparse attention** instead limits which pairs interact and changes the visibility pattern. GQA reduces distinct KV heads; FlashAttention improves execution; sparsity changes connectivity. These solve different parts of the problem and can sometimes be combined.

Think of processing movie reviews: using a more efficient working layout differs from refusing to compare distant passages. Both may save resources, but only the second changes which passages can directly interact. Evaluate that change against the task.

## 6. Serve multiple requests without wasting capacity

**Batching** processes several requests together to reuse loaded weights and keep hardware busy. Waiting to assemble a larger batch can increase latency. With **continuous batching**, a server can admit new work as completed sequences leave, instead of waiting for an entire fixed batch to finish.

**PagedAttention** organizes cache memory in blocks, reducing waste from reserving large contiguous regions and supporting controlled sharing. It manages storage; it does not eliminate the keys and values a computation needs. The [PagedAttention paper](https://arxiv.org/abs/2309.06180) describes the approach.

**Prefix caching** reuses computed state for an identical compatible token prefix. Repeated movie-assistant instructions can benefit, but similar wording is not an exact cache match. Model state, tokenization, positions, and relevant execution settings must be compatible; a changed earlier prefix generally invalidates later cached state. Prefix reuse chiefly saves prompt processing, not the generation of a new answer. See [vLLM's prefix-caching documentation](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/).

Compare these carefully: KV caching avoids recomputing earlier sequence state; prefix caching can reuse compatible state across requests; response caching reuses a finished answer. A response cache needs appropriate keys and freshness checks for changing movie availability.

## 7. Verify a cheap draft with the target model

**Speculative decoding** lets a cheaper draft mechanism propose several tokens, then asks the target model to verify them in parallel. Accepted tokens reduce the number of expensive sequential target passes. Poor acceptance or draft overhead can erase the benefit. The [speculative decoding paper](https://arxiv.org/abs/2211.17192) gives a distribution-preserving sampling algorithm.

For a greedy illustration, suppose the draft proposes “Moonlight Map is calm.” The target agrees with “Moonlight Map” but next prefers “feels”. Keep the matching prefix, append “feels”, discard the remaining draft, and continue. Verification concerns token probabilities, not whether the recommendation is factually true.

<EfficiencyDiagrams kind="speculation" />

<details className="optional-depth">
<summary>Go deeper: preserving the sampling distribution</summary>

For target distribution $p$ and draft distribution $q$ at a shared prefix, a draft token $x$ is accepted with probability $\min(1,p(x)/q(x))$. On rejection, sample a correction from the normalized positive part of $p-q$ and discard the later draft suffix. If the entire draft is accepted, the algorithm can draw an additional target token.

This correction is essential: accepting only “plausible-looking” drafts does not preserve the target distribution. Exact distributional equivalence is not a promise of identical sampled text for the same seed, nor a promise of correct facts. The workbook does not implement speculative decoding.

</details>

## 8. Distinguish sparse computation from smaller models

A **mixture-of-experts (MoE)** layer contains several expert networks and a learned router that selects a subset for each token. Experts often replace feed-forward sublayers. They are numerical networks, not separate human specialists or guaranteed genre categories. Sparse activation reduces work per token relative to running every expert, while **total parameters** still include inactive experts. The [Switch Transformer paper](https://arxiv.org/abs/2101.03961) illustrates sparse expert routing.

If an illustrative layer has eight experts and activates two, that is one quarter of its expert paths per token, not automatically one quarter of the entire model's cost. Shared layers, routing, uneven load, and communication remain. Inactive expert weights must still be stored or transferred when needed.

**Distillation** trains a student model to reproduce useful behavior from a teacher, for example from output distributions or generated demonstrations. The student can be smaller, but may lose capabilities. The [original distillation paper](https://arxiv.org/abs/1503.02531) explains learning from teacher predictions. **Pruning** removes selected weights or structures; speed improves only when the runtime can exploit the resulting structure or sparsity.

These differ from spending more computation at inference time. Generating longer deliberations, testing candidate answers, or sampling several alternatives can improve some tasks while increasing latency and cost. More computation alone does not establish correctness.

## 9. Match the system to its hardware and workload

| Strategy | What is distributed or moved | Main tradeoff |
| --- | --- | --- |
| Replicas | Separate model copies handle separate requests | More aggregate capacity, but duplicate weights |
| Tensor parallelism | Parts of a layer across devices | Frequent communication between devices |
| Pipeline parallelism | Different layers or stages on different devices | Scheduling gaps and stage balance |
| Expert parallelism | MoE experts across devices | Token routing and load balance |
| CPU/disk offloading | Some state moved out of accelerator memory | Extra transfers can slow execution |

Multiple devices do not automatically divide every memory term evenly or halve latency. For example, [tensor-parallel inference](https://huggingface.co/docs/transformers/main/en/perf_infer_gpu_multi) needs communication while combining partial layer results. The interconnect can become a bottleneck.

For the movie assistant, first identify the problem. Long review bundles can inflate prefill and cache costs; many simultaneous users can strain serving capacity; an unnecessarily long answer can waste decode time. Choose a change, measure against the same requests, and rerun recommendation-quality checks. A deployment decision needs both resource evidence and useful answers.

<details className="optional-depth">
<summary>Go deeper: inference memory is not a training budget</summary>

Training also stores gradients, optimizer state, and activations needed for backward computation. **Activation checkpointing** saves memory by recomputing selected activations during backpropagation. It trades extra computation for less stored state; it is different from saving a model checkpoint to disk.

Sharding training state can distribute parameters, gradients, or optimizer buffers. Parameter-efficient fine-tuning changes which parameters are trained, but does not necessarily remove the need to run the base model. Do not reuse this chapter's inference calculator as a training capacity estimate.

For a serving comparison, record model and tokenizer versions, precision, context lengths, concurrency, cache reuse, software, and hardware. Measure peak memory, TTFT, completion latency, throughput, and task results under the intended workload. A single average from a short prompt is insufficient evidence for a busy service.

</details>

## 12. Choose how to adapt the assistant

You can now distinguish changes to **numeric precision, cached state, attention execution, serving schedules, architecture, and hardware placement**. Each targets a different cost. Keep the measurement separate from the estimate, and the resource saving separate from the quality check.
