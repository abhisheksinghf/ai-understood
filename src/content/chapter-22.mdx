## 1. Let the input structure guide the architecture

An **architecture** specifies how layers connect and information flows. The loss and optimizer still determine what is learned. An **inductive bias** is a built-in preference for certain kinds of patterns, such as local visual patterns or dependencies across time.

| Movie input | Structure worth preserving | A possible model |
| --- | --- | --- |
| Runtime, year, genre flags | A fixed set of named features | Linear model, tree, or dense network |
| Poster pixels | Nearby pixels form edges and shapes | Convolutional neural network (CNN) |
| Ordered viewing events | Earlier events can influence later context | Recurrent neural network (RNN) or another sequence model |

These are useful starting points, not exclusive assignments. One-dimensional convolutions also process sequences; transformers can process images. A poster category is not a viewer's taste. A recommender may combine image features with catalog facts, viewing history, and an explicit ranking objective.

## 2. See how a convolution reads a local patch

A **kernel**, or filter, is a small array of weights. It slides across the image; at each position it multiplies matching values and sums them, then adds a bias. The resulting grid is a **feature map**. The same weights are reused at every position: **weight sharing**.

Our fictional grayscale poster has five identical rows `[1, 1, 0, 0, 0]`, where 1 is bright and 0 is dark. A vertical-contrast filter has three identical rows `[1, 0, -1]`. At the first position, each row contributes $1\times1+1\times0+0\times(-1)=1$. Three rows give **3**, with bias zero. Moving one pixel right gives 3 again; moving twice gives 0. The output is a 3 × 3 grid with rows `[3, 3, 0]`.

This operation does not flip the kernel; technically it is **cross-correlation**, the convention commonly called convolution in neural networks. Our filter is hand-set so its arithmetic is visible. In a trained CNN, backpropagation learns filters from the task loss; they are not all predefined edge detectors. See [D2L's convolution explanation](https://d2l.ai/chapter_convolutional-neural-networks/conv-layer.html).

## 3. Track channels, stride, padding, and pooling

An RGB image has three **channels**: red, green, and blue. One ordinary convolutional filter spans all input channels and sums their contributions into one output map. Sixteen filters produce sixteen output channels. Batch size is a separate dimension; one common layout is batch × channels × height × width. Other libraries use different axis orders. [D2L develops multi-channel convolution](https://d2l.ai/chapter_convolutional-neural-networks/channels.html).

**Stride** is how far the kernel moves per step. **Padding** adds a border, often zeros, so the kernel can operate near image edges. For input height $H$, kernel height $k$, symmetric padding $p$ on each side, and stride $s$, with dilation 1:

$$H_{\text{out}}=\left\lfloor\frac{H+2p-k}{s}\right\rfloor+1.$$

Apply the same rule to width. Our 5 × 5 input with a 3 × 3 kernel gives 3 × 3 at stride 1 without padding, 5 × 5 with padding 1, and 3 × 3 with padding 1 and stride 2. The floor discards an incomplete final placement. [Padding and stride details](https://d2l.ai/chapter_convolutional-neural-networks/padding-and-strides.html).

**ReLU** replaces negative values with zero. **Max pooling** keeps the largest value in each local window; average pooling keeps the mean. A 2 × 2 max pool with stride 2 reduces our ReLU output to the single value 3, dropping incomplete border windows here. **Global average pooling** instead averages every spatial position in each channel; our single channel becomes 2. Pooling has no learned weights in these forms and loses location information. [Pooling reference](https://d2l.ai/chapter_convolutional-neural-networks/pooling.html).

<details className="optional-depth">
<summary>Go deeper: count parameters, not output cells</summary>

For a standard convolution with groups = 1 and one bias per output channel, the parameter count is $(k_H k_W C_{\text{in}}+1)C_{\text{out}}$. A 3 × 3 convolution from 3 channels to 16 needs $(3\times3\times3+1)\times16=448$ parameters. Its output may contain thousands of values, but those are activations, not independent weights.

Flattening a 64 × 64 RGB image and connecting it to 128 dense units needs $(64\times64\times3+1)\times128=1{,}572{,}992$ parameters. These layers produce different outputs, so this is a connectivity comparison, not a matched-quality benchmark. **Dilation** spaces kernel samples apart; with dilation $d$, replace $k$ in the shape formula by the effective size $d(k-1)+1$.

</details>

## 4. Build representations from local to broad

A **receptive field** is the input region that can influence a particular activation. Two 3 × 3, stride-1 convolutions without dilation have a theoretical 5 × 5 receptive field for an interior output. Later units can combine earlier patterns over a wider region. This makes structures such as outlines and arrangements available to the model; it does not guarantee that a particular unit has a human-readable meaning.

A **backbone** is the main feature-producing network. A **head** maps its representation to the task: for example, poster-category logits, bounding-box coordinates, or a vector used with viewer features. Classification, object detection, and pixel-level segmentation require different outputs and labels.

Weight sharing helps a filter respond to a pattern in different places. It does **not** guarantee that the whole model gives identical predictions after every shift, crop, rotation, or scale change. Borders, downsampling, and the head matter. Augmentations should preserve the label: cropping away the only relevant poster detail may not.

<details className="optional-depth">
<summary>Go deeper: receptive fields and residual connections</summary>

Track a layer's receptive-field size $r$ and spacing $j$ between neighboring features in input coordinates. Start with $r=1,j=1$. A layer with kernel $k$, dilation $d$, and stride $s$ gives $r'=r+(k-1)dj$ and $j'=js$. Two 3 × 3 stride-1 layers give $r=3$, then $r=5$. A stride-2 pooling layer then changes both coverage and spacing. This describes possible connectivity, not how strongly each input actually contributes.

A **residual connection** adds an input to a learned transformation: $y=x+F(x)$ when shapes agree; a projection can align mismatched shapes. The shortcut provides a direct route for information and gradients. It does not eliminate the need for good training or guarantee that arbitrarily deep models work. See the original [ResNet paper](https://arxiv.org/abs/1512.03385).

</details>

## 5. Preserve the order of viewing events

Consider **Adventure → Adventure → Romance** and **Romance → Adventure → Adventure**. They contain the same genres but end differently. A count or mean cannot distinguish them; an ordered model can. Whether recency improves recommendations is an empirical question, not an automatic property of sequence modeling.

Represent each event by a vector: perhaps a movie embedding, watch duration, and elapsed time. An **embedding** is a learned numerical representation; our experiment instead uses the authored scalar codes adventure = +1 and romance = −1. These codes describe the watched genre, not whether the viewer liked it.

Sequence tasks differ. **Many-to-one** uses a history to produce one result, such as a next-item score. **Many-to-many** produces an output per position, such as predicting the next item after each prefix. Encoder–decoder models map an input sequence to an output sequence, possibly of another length. A next-event predictor may use only information available before that event.

## 6. Trace a recurrent network through time

An RNN maintains a **hidden state**: a numerical summary updated after each event. A simple cell uses

$$h_t=\tanh(Wx_t+Uh_{t-1}+b).$$

$W$ maps the current input, $U$ maps the previous state, and $b$ is a bias. The parameters are shared across time. A separate output head turns the state into task predictions. The state itself is not a probability. [RNN explanation](https://d2l.ai/chapter_recurrent-neural-networks/rnn.html).

Our scalar example starts at $h_0=0$ with $W=0.8,U=0.5,b=0$. The original history produces states **0.6640 → 0.8117 → −0.3749**. Reversing it produces **−0.6640 → 0.4366 → 0.7692**. Both input means are 0.3333. The different final states show order sensitivity, not measured recommendation quality.

<ArchitectureDiagrams kind="sequence" />

During training, **backpropagation through time (BPTT)** applies the chain rule to the unrolled sequence and accumulates contributions to the shared parameters. Long chains can weaken or amplify gradients, linking back to Chapter 21's vanishing/exploding-gradient problem. **Truncated BPTT** cuts the gradient path at chosen boundaries; it may carry the numerical state forward while limiting how far credit can travel. [BPTT reference](https://d2l.ai/chapter_recurrent-neural-networks/bptt.html).

<details className="optional-depth">
<summary>Go deeper: padding, masks, and the future-information boundary</summary>

Batching variable-length histories often requires padding. A padding value is a placeholder, not another movie. At a padded position our mask keeps $h_t=h_{t-1}$. Merely setting $x_t=0$ still computes $\tanh(Uh_{t-1}+b)$ and usually changes the state. Mask loss terms too when padded positions have no target. Packing sequences or selecting the last valid state are other implementation techniques.

Reset state between unrelated viewers unless you deliberately manage separate state for each. A **bidirectional RNN** reads both directions; it can be useful when the complete input is available, such as classifying a finished review. A prediction at time $t$ must not access later events through a backward state, preprocessing, or the split. Histories and labels should be constructed at their actual prediction cutoffs.

</details>

## 7. Understand why LSTMs and GRUs add gates

A plain RNN repeatedly transforms its state. **Gates** are learned controls, usually sigmoid values between 0 and 1, that regulate information flow. They are computed from inputs and state, not manual switches.

An **LSTM** (long short-term memory network) maintains a cell state as well as a hidden state. A forget gate controls how much old cell content is retained, an input gate controls new content, and an output gate controls what is exposed through the hidden state. The additive cell path can make long-range learning easier. It does not provide perfect recall. [LSTM reference](https://d2l.ai/chapter_recurrent-modern/lstm.html).

A **GRU** (gated recurrent unit) combines memory into a hidden state, using reset and update gates to control candidate computation and blending. It generally has fewer parameter groups than an LSTM of the same input and hidden size. Neither is universally better; compare accuracy, latency, and data requirements. [GRU reference](https://d2l.ai/chapter_recurrent-modern/gru.html).

<details className="optional-depth">
<summary>Go deeper: read a gate equation without memorizing it</summary>

A common LSTM formulation is $c_t=f_t\odot c_{t-1}+i_t\odot\tilde c_t$ and $h_t=o_t\odot\tanh(c_t)$. Here $f,i,o$ are forget, input, and output gates; $\tilde c$ is proposed new content; $\odot$ means elementwise multiplication. Each gate is a learned function of the current input and previous hidden state. If one coordinate has old memory 0.8, forget gate 0.9, input gate 0.2, and candidate −0.5, its new cell value is $0.9(0.8)+0.2(-0.5)=0.62$ before the output gate is applied.

One GRU convention writes $h_t=z_t\odot h_{t-1}+(1-z_t)\odot\tilde h_t$, where $z$ controls retention and a reset gate influences the candidate $\tilde h$. Some references reverse the update-gate convention, so read the equation before interpreting “open.” The workbook implements only a plain scalar RNN; it does not implement LSTM or GRU training.

</details>

## 8. Reuse a learned backbone through transfer learning

**Transfer learning** reuses knowledge learned from a source task or dataset for a target task. For posters, a backbone pretrained on broad images may supply useful features. Replace its original classification head with one matching your poster labels, or combine its features with viewer information for recommendation.

With **feature extraction**, freeze backbone parameters and train a new head. With **fine-tuning**, update some or all pretrained parameters on the target objective. With **training from scratch**, start without those learned weights. Keeping the backbone frozen does not mean that no learning occurs: the new head still learns. The [PyTorch transfer-learning tutorial](https://docs.pytorch.org/tutorials/beginner/transfer_learning_tutorial.html) illustrates both reuse strategies.

<ArchitectureDiagrams kind="transfer" />

Transfer may help with limited target labels, but mismatched source features can also hurt: **negative transfer**. A source model's accuracy or confidence does not establish target-domain accuracy. The feature-extractor contract includes expected image size, channel order, normalization, weights version, and output representation. Preserve that contract when serving predictions.

## 9. Adapt a model with a fair development process

Start with a simple baseline and a target split reflecting deployment: new movies, new viewers, or future events. Avoid near-duplicate posters or later viewing feedback crossing the relevant boundary. Train the new head first, then consider unfreezing later backbone blocks. Use validation to choose that policy and its learning rates; pretrained layers often benefit from smaller updates than a new head. Keep a separate final evaluation after selection. See [D2L on fine-tuning](https://d2l.ai/chapter_computer-vision/fine-tuning.html).

Freezing parameters, setting evaluation mode, and disabling gradient recording are different operations. For a strictly fixed backbone, prevent parameter updates **and** prevent changing state such as batch-normalization running statistics. Fine-tuning may intentionally use a different policy. If you unfreeze layers, make sure the optimizer includes them and that gradient recording is enabled through them.

<details className="optional-depth">
<summary>Go deeper: the fixed-backbone implementation boundary</summary>

This illustrative PyTorch pattern assumes a loaded backbone, a newly created head, correctly preprocessed batches, and a task-compatible loss. It is not executed by the standard-library workbook:

```python
for parameter in backbone.parameters():
    parameter.requires_grad_(False)
backbone.eval()  # also keep its dropout / running-stat behavior fixed
head.train()
optimizer = torch.optim.Adam(head.parameters(), lr=0.001)

for images, labels in target_train_loader:
    optimizer.zero_grad(set_to_none=True)
    with torch.no_grad():
        features = backbone(images)
    loss = loss_fn(head(features), labels)
    loss.backward()
    optimizer.step()
```

Here `torch` is imported separately, and the backbone must return features rather than its old class scores. Calling `train()` on a parent model can change child modes again, so reapply the intended backbone mode when needed. Unfreezing requires revisiting all three decisions: parameter flags, optimizer membership, and the no-gradient block. Cached features must be recomputed if the backbone or preprocessing changes.

</details>

## 12. Connect architectures to language

You can now ask three concrete questions about a network: **which local patterns does it reuse, how does it represent order, and which learned parts can change?** Architecture supplies a way to represent patterns; the task definition, labels, optimization, and evaluation determine whether those patterns help.
