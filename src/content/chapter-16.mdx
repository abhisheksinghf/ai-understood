## 1. Start with an information need

**Information retrieval (IR)** finds material relevant to a need from a collection. A **query** expresses that need; a **document** is the unit we retrieve; the **corpus** is the collection. Here, one movie summary is one document. Later, it might be a paragraph from a manual.

Imagine a viewer types **“space rescue”**, meaning “a story about rescuing someone in outer space.” A search engine compares that query with the catalog and returns an ordered list. It does not have to generate new text, predict a rating, or know this viewer's viewing history.

Relevance depends on the intent. A café with “no space for a kitchen” shares a word but does not answer this need. A film where “astronauts save a stranded pilot” may answer it without sharing either query word. These two mistakes will follow us through the chapter.

Our eight movies, summaries, and relevance judgments are **fictional teaching data**. We reuse familiar titles and catalog facts, adding new summaries for this search lesson. The index and scores are calculated, not authored outputs or calls to a search service.

## 2. Give documents and queries the same text rules

An **analyzer** prepares text for matching. Tokenization divides text into pieces; normalization makes selected differences equivalent. Our deliberately small analyzer lowercases and extracts runs of English letters or digits:

```text
"Space, RESCUE!" → ["space", "rescue"]
"space space rescue" → unique query terms ["space", "rescue"]
```

We keep repeated terms inside documents, because their frequency can affect ranking. We count each distinct query term once. We do not remove common words, stem words, correct spelling, or expand synonyms. Thus `rescue`, `rescues`, and `saving` are different terms. The same rules run on summaries and queries.

This is a transparent English demo, not a multilingual tokenizer or an LLM tokenizer. Titles and runtime fields are not part of its text index. See the Stanford IR book's [tokenization explanation](https://nlp.stanford.edu/IR-book/html/htmledition/tokenization-1.html).

<details className="optional-depth"><summary>Go deeper: stop words, stemming, synonyms, and phrases</summary><p><strong>Stop words</strong> are common terms that a system may omit. Removing them saves some work but can damage names, phrases, or negation: “not funny” should not silently become “funny.” <strong>Stemming</strong> reduces word forms with rules; <strong>lemmatization</strong> aims for a linguistic base form. Both can help matching and can also merge meanings you wanted separate.</p><p><strong>Query expansion</strong> adds alternatives such as rescue → save. It may recover missed films but also introduce irrelevant meanings. Evaluate it on several intents. Phrase search needs order and adjacency: documents containing both “space” and “rescue” need not contain the phrase “space rescue.” A positional index can check neighboring token positions. Our workbook stores positions for inspection but implements only OR/AND term matching; quote characters are punctuation, not a phrase operator. See <a href="https://nlp.stanford.edu/IR-book/html/htmledition/positional-indexes-1.html">positional indexes</a>.</p></details>

## 3. Build an inverted index

A simple scan checks every document for each query. An **inverted index** reverses the lookup: a term points to the IDs of documents that contain it. Each entry in this **posting list** can also store its frequency and positions.

<RetrievalDiagrams kind="index" />

For `space`, the list is M004, M005, M008. Its **document frequency**, $df$, is 3. Inside M008, `space` appears twice, so its **term frequency**, $tf$, is 2. Counting four occurrences across three documents would not make $df=4$.

An index trades construction work and storage for faster repeated lookup. New or changed summaries need index updates; deleting a document must eventually remove its searchable content too. Our small workbook rebuilds its index on each run. A larger application typically maintains a persistent index. See [building an inverted index](https://nlp.stanford.edu/IR-book/html/htmledition/a-first-take-at-building-an-inverted-index-1.html).

## 4. Separate matching, filters, and ranking

For `space rescue`, **OR** takes the union of the two posting lists: a movie may contain either word. **AND** takes their intersection: it must contain both. In our catalog OR finds five movies; AND finds M004 and M008. AND does not require adjacent words or an understanding of the whole request.

A **hard filter** enforces a structured requirement. “Known runtime below 120 minutes” uses the runtime field, excluding 140-minute City Sprint and unknown-runtime Unlisted Voyage. A high text score cannot override that requirement. Unknown is not the same as short.

<RetrievalDiagrams kind="ranking" />

**Ranking** orders the eligible matches. **Top-K** returns up to K of them. Apply required filters before truncating to K; otherwise, filtering an already-short list can leave gaps while valid candidates farther down are never considered. Query words like `under 120 minutes` do not automatically become numeric filters in this demo: use its runtime control.

<details className="optional-depth"><summary>Go deeper: fields, exact lookup, and two-stage search</summary><p>A real catalog can index title, synopsis, cast, and tags separately. A title match may deserve a field boost; a movie ID may require exact lookup. Choose normalization per field instead of running every value through one analyzer. Explicit filters can narrow genre, language, availability, or access permissions without treating them as soft preferences.</p><p>Large search systems often retrieve a broad candidate set cheaply, then apply a more expensive <strong>reranker</strong> to that set. Candidate count and final K are different controls. A reranker can reorder what it receives; it cannot recover a relevant document excluded before that stage. Index compression, caching, and distributed partitions address scale, but they do not repair a poorly defined relevance task.</p></details>

## 5. Understand term overlap and TF-IDF

Our first baseline gives one point per distinct query term present. M004 and M008 both match two terms, so they tie at 2. Movie ID breaks exact ties. This is easy to inspect, but it ignores frequency and whether a term is rare.

**TF-IDF** combines term frequency with **inverse document frequency**: repeated evidence within a document can help, while a term found almost everywhere is less discriminating. There are several variants. Our score is an unnormalized sum of log-TF weights, using natural logarithms:

$$
s(q,d)=\sum_{t\in q,\;tf(t,d)>0}(1+\ln tf(t,d))\,\ln\frac{N}{df(t)}.
$$

$N$ is the number of indexed documents, here 8. For M004, both term counts are 1: `space` contributes $\ln(8/3)=0.9808$ and `rescue` contributes $\ln(8/4)=0.6931$. Total: **1.6740**. M008 repeats both terms, so this variant scores it **2.8343**.

Absent terms contribute zero. A term in every document has zero IDF under this formula. Matching and scoring remain separate: a matching document may have a zero score. See [TF-IDF weighting](https://nlp.stanford.edu/IR-book/html/htmledition/tf-idf-weighting-1.html).

<details className="optional-depth"><summary>Go deeper: sparse vectors and score conventions</summary><p>Give each vocabulary term one coordinate. A TF-IDF document vector is <strong>sparse</strong>: most coordinates are zero. One common alternative ranks by cosine similarity between weighted query and document vectors. That normalizes by vector lengths; our sum does not. Document and query weighting, smoothing, logarithm base, and normalization all affect numerical scores.</p><p>Do not compare a raw score from one formula with a score from another as if they shared a calibrated scale. Compare their ordered results against the same relevance judgments. Dense learned embeddings are another representation, introduced in Chapter 17; a sparse lexical vector is already a vector without being a neural embedding.</p></details>

## 6. Improve the lexical baseline with BM25

BM25 also rewards matching terms, but adds two useful controls: repeated occurrences give **diminishing returns**, and term frequency is adjusted for **document length** relative to the collection. Repeating “space” ten times should not simply produce ten times the evidence.

Our exact teaching variant is:

$$
\mathrm{IDF}(t)=\ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right),
$$
$$
s(q,d)=\sum_{t\in q}\mathrm{IDF}(t)\,
\frac{tf(t,d)(k_1+1)}{tf(t,d)+k_1(1-b+b|d|/\mathrm{avgdl})}.
$$

$|d|$ counts summary tokens; **avgdl** is their average across all eight documents: $94/8=11.75$. We use $k_1=1.2$ and $b=0.75$. Larger $k_1$ lets extra repetitions contribute more; $b=0$ removes length normalization. At $k_1=0$, a present term contributes its IDF regardless of count or length; missing terms still contribute zero.

For M004, $|d|=10$ and both counts are 1. The frequency/length factor is $2.2/[1+1.2(0.25+0.75\times10/11.75)]\approx1.0649$. Multiply each term's BM25 IDF by this factor, then sum: **1.7439**. M008 scores **2.1863**, so it ranks first.

These scores are **weights, not relevance probabilities**. We use the positive IDF form documented by [Apache Lucene](https://lucene.apache.org/core/9_9_1/core/org/apache/lucene/search/similarities/BM25Similarity.html), with explicit token counts and the formula above; we do not claim byte-for-byte score equivalence with Lucene. The [Stanford BM25 treatment](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html) explains the underlying family and alternative forms.

## 7. Recognize what lexical scoring cannot fix

Default BM25 returns **Parallel World, Quiet Orbit, Cafe Chaos**. The first two fit the space-rescue intent. Cafe Chaos contains “space” in another sense. Unlisted Voyage fits the intent but its summary says “astronauts save a stranded pilot,” so neither query term has a posting for it.

Changing BM25 parameters can reorder matches, but cannot add a movie with no shared terms to this candidate set. Switching to AND removes Cafe Chaos, yet still misses Unlisted Voyage. Returning five results does not fix that missing candidate either.

Common failure patterns include vocabulary mismatch, ambiguous words, spelling errors, overly strict filters, stale summaries, and the needed fact being absent from the collection. Inspect the missed or incorrect movie before deciding whether to change the analyzer, metadata, query expansion, or retrieval method. A more elaborate scorer is not a universal repair.

## 8. Judge the ranked list against the intent

The ranking algorithm never reads our relevance labels. Separately, we authored binary judgments for each of three preset intents across all eight movies. For `space rescue`, M004, M007, and M008 are relevant; the other five are nonrelevant.

With default BM25 and K = 3, two returned movies are relevant out of three relevant movies in the corpus:

| Measure | This chapter's definition | Default result |
| --- | --- | --- |
| Precision@K | Relevant results in the first K slots / K | 2/3 = 66.67% |
| Recall@K | Relevant results in those slots / relevant eligible movies | 2/3 = 66.67% |
| Reciprocal rank@K | 1 / rank of the first relevant result; 0 if absent in top K | 1/1 = 1 |

We count empty result slots as zero for Precision@K. With AND, only two movies are returned: both are relevant, but **Precision@3 stays 2/3** under that convention. Precision among returned items would be 2/2; it answers a different question.

The runtime filter removes unknown-runtime M007 from eligibility. Recall becomes 2/2 = 100% **for that smaller task**, not because the search discovered the missed movie. We show no relevance metrics for arbitrary queries without judgments. When there are no relevant eligible documents, recall is undefined. See [evaluating ranked results](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html).

<details className="optional-depth"><summary>Go deeper: query sets, MRR, MAP, and NDCG</summary><p><strong>MRR</strong> averages reciprocal rank over queries, so it emphasizes the first useful result. Our explorer shows one query's truncated reciprocal rank, not a dataset-wide MRR. <strong>Average precision</strong> rewards retrieving relevant documents early across a ranking; <strong>MAP</strong> averages that measure over queries. Specify cutoffs and missing-result conventions.</p><p><strong>NDCG</strong> supports graded relevance. A common gain is 2<sup>grade</sup> − 1, discounted by log<sub>2</sub>(rank + 1). Sum to K and divide by the ideal ranking's sum. If the ideal sum is zero, choose and document a reporting convention. These additional metrics are explained here, not implemented in the workbook.</p><p>Three authored queries cannot establish production quality. Use representative query sets and independently judged results; tune on development queries and reserve others for evaluation. Unjudged is not inherently nonrelevant, and clicks can reflect position or presentation rather than true relevance. Report per-intent failures along with averages, latency, and coverage.</p></details>

## 12. Connect search to embeddings and RAG

You can now trace **need → analyzed query → posting lists → eligible candidates → ranking → top-K → relevance evaluation**. Keep each boundary visible when something goes wrong.

<RetrievalDiagrams kind="bridge" />

In **retrieval-augmented generation (RAG)**, a generator receives retrieved material as context for answering. Retrieval can use keywords, embeddings, or a combination; RAG does not inherently require a vector database. A useful retrieved passage can support an answer, but retrieval alone does not guarantee source quality, factual correctness, or faithful use of the passage.

**Chapter 17: Embeddings and vector search** tackles matching beyond literal shared words. We will keep this keyword baseline so that a new representation has something concrete to improve upon.
