## 1. Start with the question each term answers

Imagine someone saying, “Our chatbot is AI, ML, deep learning, GenAI, an LLM, RAG, and an agent.” Some of these labels might fit, but they do not all name the same thing.

Ask what each label tells you:

| Question | Relevant terms | What they describe |
|---|---|---|
| What broad field are we working in? | AI | Building systems that perform tasks associated with intelligence |
| How is behavior learned? | ML, deep learning | Families of learning methods |
| What kind of problem is being solved? | NLP | Problems involving human language |
| What capability is being used? | Generative AI | Producing content, such as text, images, or audio |
| What model is inside? | LLM | A large language model |
| How are components connected? | RAG, workflows, agents | Ways to supply information and organize execution |
| How broad is the capability we want? | AGI | A research concept concerning general intelligence |

The most useful nesting relationship is **deep learning within machine learning within AI**. The other terms need different relationships.

Read the boxes as “is a kind of,” not “must come next.” A decision tree can be ML without deep learning. Language processing can use hand-written rules. An LLM application can use retrieval, tools, both, or neither.

## 2. Machine learning and deep learning

**Machine learning (ML)** fits a model using data and a learning objective. Instead of writing every decision rule yourself, you choose a learning procedure that adjusts the model from examples. You still decide what to measure and whether its performance is useful.

For a movie-review classifier, the task is to predict a review's sentiment. A training example pairs a review such as “A cheerful adventure I would watch again” with a label such as “positive.” A **label** is the target answer supplied for that example; a **feature** is an input value available to the model.

A model might learn from features such as review length, counts of selected words, and movie genre. A **decision tree** learns a sequence of branching tests on these features. It is an ML method; it does not need a neural network.

**Deep learning (DL)** uses neural networks with multiple layers of learned transformations. A layer converts its input values into a new representation. Training adjusts the numerical settings, called **parameters**, across the network so that its outputs better meet the objective.

For language, learned representations can encode useful patterns in words and their context. That can reduce the need to manually design every feature. It does not remove the need for suitable data, evaluation, or application logic.

**Same task, different method:** a decision tree and a deep neural network can both classify reviews. Neither has to generate a recommendation explanation. Choose between them using measured results, data needs, cost, and complexity. “Deep” describes the model structure; it does not guarantee deeper understanding.

<details className="optional-depth">
<summary>Go deeper: what is a learned representation?</summary>

A representation is a numerical form of information that a model can work with. A manually chosen feature might be “does the review contain the word enjoyable?” A learned representation can capture combinations of signals that are useful for the training objective, including context that an isolated word misses.

For example, “I loved this movie” and “A really enjoyable film” may acquire related representations when training rewards handling them similarly. This is not guaranteed by the architecture alone. Data, objectives, and training quality matter. Later chapters explain embeddings, layers, and parameter updates mathematically.

“More layers” and “more parameters” are related design choices, but not synonyms. A layer can be wide or narrow, and different network designs use their parameters differently.

</details>

## 3. NLP is a field of problems

**Natural language processing (NLP)** concerns computational work with human language: classifying messages, finding names, translating, searching text, summarizing, and more.

NLP tells you **what the system works on**, not exactly how it works. Finding a movie ID in a catalog entry might use a written matching pattern. Classifying its topic might use a small ML model. Drafting a readable response might use an LLM. All involve language; only some require generation.

Consider “Movie MOV-104 lasts 105 minutes.” Extracting “MOV-104” and “105” into fields is an NLP task. A pattern matcher can handle this standardized input without learning from examples. More varied language may require a different method.

An LLM is one powerful tool for NLP, not a replacement name for the whole field. [Hugging Face's NLP and LLM introduction](https://huggingface.co/learn/llm-course/chapter1/1) develops this distinction.

## 4. Generative AI and LLMs

**Generative AI (GenAI)** produces content from learned patterns, usually in response to some input. Examples include writing a summary, generating an image from a description, or producing speech from text.

**A large language model (LLM)** is a language model trained at substantial scale. “Large” has no universal numerical cutoff. Modern LLMs use deep learning; many familiar text generators use transformer networks, which we will unpack later.

An LLM represents text as **tokens**: units that may be words, word pieces, or punctuation. In the common next-token approach to generation, it estimates possibilities for the next token from the available context; a decoding procedure selects a token and continues. This mechanism can produce an explanation or code, but does not itself guarantee factual correctness.

For our assistant, “Explain why this movie fits my preferences” is a **prompt**, the input containing instructions and any supplied material. The **context window** is the model's bounded working input/output capacity, measured in tokens according to the model's limits. It is not an unlimited memory of everything the user has ever said.

Two distinctions keep this clear:

- **GenAI extends beyond LLMs.** Image and audio generators can use other model families.
- **An LLM can perform a classification task.** Asking it to return only “positive” uses a generative model to produce a label. The application task is still classification.

The model is also different from the chat application around it. A chat interface may add document uploads, stored history, search, permission checks, and tool execution. Those features are not automatically inside the model.

<details className="optional-depth">
<summary>Go deeper: context, parameters, and foundation models</summary>

**Parameters** are numerical values fitted during training. **Context** is information supplied for a particular inference call. Pasting a new movie description into context can change the answer without changing the parameters.

**Fine-tuning** means additional training that updates model parameters. This is different from prompting or retrieving documents. An application might store conversation history and include it in later prompts; that is not, by itself, fine-tuning.

A **foundation model** is trained broadly and can be adapted to different tasks. The term is wider than LLM: it can include vision and multimodal models. A **multimodal** model handles more than one kind of information, such as text and images. Exactly which inputs and outputs it supports depends on the model.

The boundaries of “large” and “foundation” are conventions rather than a universal size test. Focus on the model's supported tasks, measured behavior, and operating requirements.

</details>

## 5. RAG supplies information before generation

Suppose the user asks: **“Which light adventure movies in this catalog run under two hours?”** A model's training does not ensure it knows this catalog or its latest entries.

**Retrieval-augmented generation (RAG)** connects retrieval with generation. The application finds relevant information, includes it in the generator's context, and asks for an answer based on that evidence.

<ConceptDiagrams kind="rag" />

In our fictional example, the retrieved entry says: “Moonlight Map is an adventure comedy lasting 105 minutes.” A suitable answer recommends it based on those facts and cites the entry. It should not invent a streaming service that the entry never names.

Retrieval can use keywords, numerical representations called embeddings, or a combination. A vector database is one implementation option, not the definition of RAG. Here, **retrieval supplies context; it does not itself retrain the generator**. [Microsoft's RAG overview](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview) explains the retrieval-and-generation pattern.

RAG adds evidence, not certainty. Search might miss the relevant passage, retrieve an obsolete version, or return a passage the model misinterprets. Check retrieval quality and whether the answer's claims are actually supported. A citation alone is not proof that a claim follows from its source.

<details className="optional-depth">
<summary>Go deeper: how the documents become searchable</summary>

A common preparation path is to extract document text, divide it into useful passages called **chunks**, and build an **index**, a structure used to find candidates efficiently. Keep document names, versions, and locations with each passage.

At question time, retrieval selects passages; the application constructs the model input; generation produces the answer. Preparing the collection and answering a question are separate activities. A saved index can become stale if changes in the source documents are not reflected in it.

Manually pasting one passage gives a model context. It does not demonstrate an application that automatically retrieves relevant information. Likewise, search that only returns links does not contain the generation step of RAG.

</details>

## 6. Workflows, tools, and agents

A **tool** is a function an application makes available, such as searching a movie catalog, reading a review, or adding movie lengths. When a model requests a tool call, application code validates and executes the allowed function and returns its result. The request itself is not execution.

A **workflow** organizes steps. In a fixed workflow, code defines the route: retrieve catalog entries, draft an answer, check the required fields, then send the draft for review. The workflow can contain model calls, conditions, and retries.

In the **LLM agent** sense used here, the model can choose the next step based on the goal and observations. It might search, inspect a movie entry, search again with a different phrase, then decide it has enough evidence to respond. This creates a loop.

<ConceptDiagrams kind="agent" />

The difference is control over the next step. One tool call, a chat interface, or a long sequence of steps does not by itself establish an agent. Definitions vary; [Anthropic's engineering guide](https://www.anthropic.com/engineering/building-effective-agents) uses this distinction between predefined workflows and model-directed execution.

An agent can use RAG as part of its work. RAG can also run in a fixed workflow with no agent loop. Neither requires the other.

For our assistant, read-only access to a catalog may be enough. If it can rent a movie or change a watchlist, define the allowed actions, validation, and review requirements. Set stopping conditions and tool-call limits so an unsuccessful search cannot continue indefinitely.

<details className="optional-depth">
<summary>Go deeper: why “agent” has more than one meaning</summary>

In broader AI, an agent is a system that perceives an environment and acts in it. It need not contain an LLM; a game-playing system or robot controller can fit this description.

This handbook uses the narrower phrase **LLM agent** when discussing a model that helps determine the sequence of tool use and other steps. Always describe the actual control loop, permissions, and stopping rules instead of relying on the product label.

</details>

## 7. Put the pieces into one application

Our fictional **movie assistant** receives preferences, searches a supplied catalog, drafts an answer with sources, and gives the user a reviewable result.

## 8. Where AGI fits

**Artificial general intelligence (AGI)** is a research concept concerned with broad capability across tasks and situations, rather than competence on only a restricted set. Definitions differ on the breadth, performance level, and autonomy required.

AGI is therefore not another component to add after RAG or agents. A proposed framework, [Levels of AGI](https://arxiv.org/abs/2311.02462), separates questions such as breadth and performance when describing progress. It is a framework, not a universally accepted test.

An assistant that reads movie posters and writes useful recommendations demonstrates those capabilities. That evidence alone does not establish general intelligence. **Multimodal** describes information types; **agentic** describes aspects of execution; neither establishes AGI.

For practical work, use narrower, testable claims: “On this held-out set of movie requests, the system found entries meeting the genre and runtime constraints in these cases.” A **held-out set** contains examples excluded from fitting the system, used to assess its behavior on new cases. We will examine evaluation in later chapters.

## 9. Choose from the need

Start by writing the required input, output, and success criterion. Then choose a baseline simple enough to understand and test.

| Need in the movie assistant | A sensible starting point | What you would check |
|---|---|---|
| Check whether a movie fits a 120-minute limit | Ordinary arithmetic | Correct runtime and units |
| Predict a movie review's sentiment | Rules or a small classifier as a baseline | Errors by sentiment on new reviews |
| Explain a suggestion from supplied movie facts | A template or an LLM, compared on the task | Coverage of facts and unsupported claims |
| Answer from a changing movie catalog | Search; add RAG when a composed answer is needed | Retrieval relevance and evidence support |
| Choose follow-up searches based on results | Start with an explicit workflow; consider an agent if flexibility helps | Task success, tool mistakes, time, and cost |

No technique is automatically required because another is present. A classifier does not need to write prose. A movie search tool need not generate an answer. A RAG assistant need not choose its own workflow.
