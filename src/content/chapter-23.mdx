## 1. Start with the language task

**Natural language processing (NLP)** studies computational methods for human language. It includes recognizing structure and meaning, extracting information, and producing text. A language model is one tool within NLP; it is not the definition of the whole field.

| Movie application | Task | What a useful output looks like |
| --- | --- | --- |
| “The ending was wonderful.” | Sentiment classification | A label or score, assessed against a defined annotation policy |
| “Find an adventure under 120 minutes.” | Information extraction | Genre = adventure; maximum runtime = 120 |
| “What did reviewers like about it?” | Summarization / question answering | A concise answer supported by the supplied reviews |
| “this movie is …” | Language modeling | A probability distribution over the next token |

**Syntax** concerns how expressions are structured; **semantics** concerns meaning; **pragmatics** concerns meaning in a situation. “Not a bad movie” illustrates why individual words are insufficient. A practical system needs a clear input/output contract, suitable examples, and task-specific evaluation—not just fluent text.

## 2. Decide what counts as a token

A **token** is a unit the model consumes or predicts. It may be a word, punctuation mark, word fragment, character, or byte-based piece. A **vocabulary** maps allowed pieces to token IDs. Token boundaries depend on the tokenizer; one word is not necessarily one token.

Word tokenization is easy to read but struggles with names, spelling variations, and unseen words. Character tokenization uses smaller units but longer sequences. **Subword tokenization** balances reuse and sequence length: a rare word may be represented by familiar smaller pieces. A tokenizer with all 256 byte values available can represent any valid UTF-8 input through those bytes, though individual tokens need not decode to complete characters.

Preprocessing changes the information available. Lowercasing merges “US” and “us”; removing punctuation can lose sentence structure; deleting “not” reverses the meaning of a review. Use the preprocessing expected by the model instead of applying generic text cleaning automatically.

<details className="optional-depth">
<summary>Go deeper: normalization, stemming, and lemmatization</summary>

**Normalization** makes chosen surface forms consistent, for example a Unicode normalization policy or standardized line endings. It can be useful, but it is not always reversible. Keep original text when exact quotations or offsets matter.

**Stemming** applies rules to shorten words, sometimes producing a fragment. **Lemmatization** maps inflected forms to a dictionary form using linguistic information. They can help a particular search pipeline, but are not mandatory preparation for a pretrained language model. Likewise, stop-word removal may suit some retrieval designs while damaging negation or grammatical context in another task. Measure the effect on the actual task.

</details>

## 3. Learn how byte-pair encoding builds reusable pieces

**Byte-pair encoding (BPE)** repeatedly merges a frequent adjacent pair of existing units into a new unit. A training phase learns an ordered merge list; encoding new text then applies those learned rules. It does not relearn a vocabulary for every question. The [original subword BPE paper](https://aclanthology.org/P16-1162/) explains the motivation for rare-word handling.

Our teaching version starts with 256 UTF-8 byte tokens. On the six movie sentences, the first winning pair is byte 115 (“s”) followed by byte 32 (space), observed 10 times. It becomes ID 256. The next merge combines byte 105 (“i”) with ID 256 to form `is␠`, ID 257. Here **␠ is only a display symbol for a space**.

With 16 merges, `this movie is fun.` becomes four pieces: `this␠movie␠is␠`, `f`, `un`, and `.`. Their IDs are **270, 102, 268, 46**. Concatenating their underlying bytes reconstructs the original text. The joined phrase is possible because this simple tokenizer allows merges across spaces; many production tokenizers restrict merging within pre-tokenized regions.

<details className="optional-depth">
<summary>Go deeper: a precise tokenizer contract</summary>

The workbench counts adjacent pairs separately within each training sentence, including overlapping occurrences. It chooses the greatest count, breaking ties by smaller left ID and then smaller right ID. Replacements run left to right without overlap. It stops at the requested merge budget or when no pair occurs twice. New IDs start at 256; encoding applies the merge list in training order. All base bytes remain available.

Real tokenizer families differ. BPE learns merges; **WordPiece** uses a different vocabulary-building procedure; **Unigram tokenization** selects pieces using a probabilistic vocabulary model. SentencePiece is a toolkit that supports methods including BPE and Unigram; it is not a synonym for one algorithm. See the [SentencePiece paper](https://aclanthology.org/D18-2012/). Always pair the tokenizer files, normalization settings, special-token rules, and vocabulary version with the model that expects them.

</details>

## 4. Separate token IDs from learned representations

ID 270 is a lookup key, not a meaning score. The difference between IDs 270 and 102 says nothing about semantic similarity. In a neural model, an **embedding table** stores a learned vector for each ID. A vocabulary of 1,000 entries with embedding dimension 64 has 64,000 embedding values. Looking up five tokens produces five vectors of length 64.

Context-processing layers combine those vectors. A token's contextual representation can differ between “a light comedy” and “a light above the stage.” Order must also be represented, through recurrence, positional information, or another architecture mechanism. Tokenization alone does not provide comprehension.

**Special tokens** have designated roles. A beginning marker can start a sequence; an end marker can tell a generator to stop; padding fills unused batch positions. A padding mask prevents placeholders from acting as real content. The exact symbols and insertion rules are model-specific: typing a marker's visible spelling is not universally equivalent to inserting its special ID.

<details className="optional-depth">
<summary>Go deeper: Unicode, bytes, and context budgets</summary>

A displayed character can contain multiple Unicode code points, and a code point can occupy several UTF-8 bytes. The clapperboard emoji 🎬 is one code point and four UTF-8 bytes. This tokenizer's ASCII training corpus does not merge those bytes, so the emoji uses four tokens. Some byte fragments are invalid text on their own; the explorer displays their hexadecimal values and decodes only after concatenation.

A **context window** limits the token positions a model can process under its supported configuration. Input, formatting markers, and generated output consume capacity according to that system's rules. Token counts vary with language, whitespace, numbers, and the tokenizer. There is no reliable universal “one token equals one word” conversion. A longer window increases possible access, not a guarantee that every detail will be used well.

</details>

## 5. Define a language model as a probability model

A language model assigns probabilities to token sequences. The chain rule decomposes a sequence into next-token predictions:

$$P(x_1,\ldots,x_n)=\prod_{t=1}^{n}P(x_t\mid x_1,\ldots,x_{t-1}).$$

An **autoregressive** model predicts using the earlier prefix and then can extend it one token at a time. A **unigram** model ignores previous tokens. A **bigram** model uses only the immediately previous token. More generally, an **n-gram** uses at most the previous $n-1$ tokens. These are explicit context limitations, not claims that language itself has such a short memory. [D2L's language-model chapter](https://d2l.ai/chapter_recurrent-neural-networks/language-model.html) develops this sequence view.

Our bigram is fitted by counting lowercase words and punctuation in six authored sentences. It has 13 possible target tokens, including an end token and an unknown token. The beginning marker is a context, never a target. This is a separate word tokenizer; it does not use the BPE IDs from the first experiment.

After `is`, the corpus has `fun` twice, `slow` once, and `warm` once. The unsmoothed estimate is $P(\text{fun}\mid\text{is})=2/4=0.5$. Both “this movie is” and “this film is” produce the same next-token distribution in this model because their last token is identical.

## 6. Handle unseen transitions and define training targets

Observed counts alone assign zero probability to unseen transitions. **Additive smoothing** adds a nonnegative value $\alpha$ to each possible target count:

$$P(w\mid h)=\frac{C(h,w)+\alpha}{C(h)+\alpha V}.$$

$h$ is the previous token, $C(h,w)$ the pair count, $C(h)$ the number of observed continuations, and $V$ the target-vocabulary size. With $\alpha=1$, our example gives $(2+1)/(4+13)=3/17\approx0.1765$. The remaining probability has been distributed across other candidates. Smoothing avoids zero probabilities here; it does not recover missing knowledge or necessarily improve every score. With $\alpha=0$ and no observations for a context, our generator reports that no continuation is available.

Neural language models learn parameters instead of storing only a count table. **Self-supervised learning** obtains targets from the text itself: each observed next token is a training label. In **teacher forcing**, training supplies the observed prefix rather than the model's previous sampled guesses. The inputs and targets are shifted by one position.

<LanguageDiagrams kind="targets" />

At each position, the output head produces **logits**: unrestricted scores over the vocabulary. Softmax converts them to probabilities. Cross-entropy for the correct target is $-\ln p_{\text{target}}$; backpropagation adjusts parameters to reduce the average loss. Seeing the target through the input or future context would make the training problem invalid. A causal architecture must block that access even when many training positions are processed together.

## 7. Interpret loss and perplexity carefully

A target given probability 0.5 contributes $-\ln(0.5)\approx0.6931$ **nats** of loss; probability 0.1 contributes about 2.3026. Nats use the natural logarithm. Higher probability on the observed target gives lower loss.

For $N$ scored targets, mean negative log-probability is $L=-\frac{1}{N}\sum_t\ln p_t$, and **perplexity** is $\exp(L)$. Equivalently, it is the inverse geometric mean of the observed-target probabilities. A uniform distribution over $V$ candidates has perplexity $V$; a general perplexity is not literally the number of choices at each position.

Our familiar sentence `this movie is fun .` has six targets when the end token is included. Without smoothing their probability product is $1/8$, so $L=\ln(8)/6\approx0.3466$ and perplexity is **1.4142**. With add-one smoothing, its perplexity becomes **4.2178**. This visible training sentence cannot establish which policy generalizes better.

<details className="optional-depth">
<summary>Go deeper: fair perplexity comparisons and unknown words</summary>

Compare perplexities only under compatible tokenization, text, context, masking, and boundary policies. Different token units change the number and difficulty of predictions. For fixed-window models, chunking can discard useful context; a sliding evaluation window needs a clear rule for which positions are scored. See the [Hugging Face perplexity guide](https://huggingface.co/docs/transformers/main/en/perplexity).

In our word model, `dazzling` maps to the unknown symbol because it is outside the vocabulary. With no smoothing, two transitions in that mapped sentence have probability zero, so loss and perplexity are infinite. JSON reports `null` for these infinite metrics and supplies the zero-probability count. With smoothing the score is finite, but it is still the probability of the **mapped token sequence**, not of the exact unseen spelling. The byte tokenizer has no such unknown-token fallback because every input byte has an entry.

</details>

## 8. Generate text by choosing and feeding back tokens

Generation repeatedly computes a distribution, selects a token, and appends it to the prefix. It ends at a stop condition, such as an end token or an output limit. During generation, an earlier mistake can become part of the next input.

**Greedy decoding** chooses the highest-probability token at each step. It need not find the most probable complete sequence. **Sampling** draws from a distribution, allowing alternatives. A random seed makes a run reproducible under the same implementation; it does not make the output more correct.

**Temperature** $T>0$ rescales logits before softmax: $q_i\propto\exp(z_i/T)$. Lower temperature sharpens differences; higher temperature flattens them. Given base probabilities directly, the equivalent rule is $q_i\propto p_i^{1/T}$. Positive temperature alone preserves the ranking, so greedy choices do not change unless other rules or numerical details intervene.

**Top-k sampling** keeps the k highest-scoring candidates and renormalizes. **Top-p**, or nucleus sampling, keeps a smallest high-probability prefix of the sorted candidates whose cumulative mass reaches a chosen threshold. These are decoding policies, not changes to learned weights. The workbench implements temperature and top-k; top-p is explained only. [Generation parameter reference](https://huggingface.co/docs/transformers/main/en/main_classes/text_generation).

## 9. Distinguish language likelihood from task success

A frequent phrase can be false. A rare name can be correct. A next-token probability measures a model's continuation preference under its inputs and training, not the probability that a whole claim is true. Raising temperature does not add evidence; lowering it does not verify a streaming-availability claim.

Choose evaluation for the application: extraction needs field-level checks; a review classifier needs classification metrics; a grounded answer needs evidence and citation checks. Keep independent evaluation text separate from tokenizer/model fitting and from repeated tuning. Duplicated reviews, related documents, or future data crossing a split can inflate apparent quality.

<details className="optional-depth">
<summary>Go deeper: causal prediction, masked prediction, and instruction following</summary>

A **causal language-model objective** predicts each next token from its earlier context. A **masked language-model objective** predicts selected hidden or corrupted tokens using the permitted surrounding context, as illustrated in the [BERT paper](https://aclanthology.org/N19-1423/). Their conditioning differs, so ordinary next-token perplexity does not directly apply to a masked model. Encoder–decoder objectives can condition an output sequence on another input sequence, such as a review to summarize.

Learning to predict text supplies a useful training signal, but a base model is not automatically a reliable instruction-following assistant. Later adaptation, preference training, retrieval, tools, and application checks address different needs. Those topics build on this foundation in later chapters. A successful tokenizer round trip or low training loss is evidence about a specific mechanism, not mastery of the user's task.

</details>

## 12. Connect language modeling to attention

You now have the full chain: **text → token IDs → representations → next-token scores → a selection rule**. Tokenization chooses the units, the model estimates probabilities, and decoding chooses how to continue. Keep those responsibilities distinct when debugging.

The bigram's weakness is concrete: it cannot distinguish two prefixes ending in the same token. **Chapter 24: Attention and transformers explained** will show how a neural architecture can combine information from many permitted positions rather than relying on one previous token or a single recurrent state.
