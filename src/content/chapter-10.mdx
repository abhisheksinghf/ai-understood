## 1. Build one useful vertical slice

A **vertical slice** is one small task working from input to visible result. Our task is: take learner preferences and note entries, produce a structured suggestion, and show it for review. We begin with a **command-line interface (CLI)**: a Python program you run from a terminal. A web interface can later call the same application logic.

This is **inference**: using an existing model to produce a response. We are not training weights, building a search index, or creating an autonomous agent. No framework is required for this first workflow. Python's standard library can read JSON, make HTTPS requests, validate results, and run tests.

This first learning-assistant app uses supplied preferences and note records to guide an LLM’s suggestion and explanation. It does not retrieve from a large collection, train a model, create a quiz, or change a calendar yet.

Reuse Chapter 9's fictional study-session case: S1 asks for an introductory note about model learning, estimated at no more than 30 minutes. S2 lists Overfitting, an introductory learning note estimated at 20 minutes, and Embeddings, an advanced search note estimated at 45 minutes. S3 says Overfitting's exam date is not supplied. A useful suggestion explains why Overfitting fits and keeps the exam date unknown. The learner profile, estimates, and dates are teaching examples.

The result has two layers: the **application status**, such as `review_required`, and an optional **candidate recommendation** with `recommendation`, `exam_date`, `evidence_ids`, and `open_questions`. A failure returns a status without an accepted candidate. This prevents “something went wrong” from masquerading as a valid study suggestion.

## 2. Separate the workflow from the provider

An **adapter** translates between your application and an external interface. Here the workflow asks a provider to generate a response, then processes what comes back. It does not need to know whether that provider returns a prepared fixture or contacts a model service.

<ApplicationDiagrams kind="flow" />

A **fixture** is prepared test data. Our offline provider returns authored responses, including deliberately broken ones. The validation and control flow are real Python execution; the language-model behavior is simulated. This lets us test rare failures repeatedly without network access or charges.

| Workbook file | Responsibility |
|---|---|
| app.py | Validate sources, build requests, run the workflow, expose the CLI |
| provider.py | Make the optional HTTPS call and classify transport errors |
| errors.py | Share one provider-error type between modules |
| fixtures.json / sources.json | Authored outcomes / fictional input records |
| test_app.py | Check the workflow and adapter using local test doubles |
| README.md | Run instructions, boundaries, and live setup |

**Dependency injection** means supplying a dependency from outside a function. The important call is `run_recommender(sources, provider, max_attempts=1)`. Tests pass a fixture provider; live mode passes an API provider. Changing that argument changes where responses come from without duplicating the rest of the app.

<details className="optional-depth">
<summary>Go deeper: functions, adapters, SDKs, and frameworks</summary>

The provider interface is deliberately small: a `model` name and a `generate(request)` method. A **test double** is a substitute for a dependency used in a test; our fixture provider is one. A real provider adapter must normalize its actual API into the envelope expected by the workflow. Another vendor cannot simply be swapped in by changing an endpoint string.

An **SDK** is a library that wraps a service's protocol in language-friendly objects and methods. It may handle authentication headers, serialization, typed responses, and retries. Our teaching adapter uses Python's built-in HTTP facilities so those boundaries remain visible and offline setup needs no packages. The [official OpenAI libraries](https://developers.openai.com/api/docs/libraries) are an alternative when building further; inspect their retry behavior before adding an outer retry loop.

A web framework handles concerns such as routes and request parsing. An orchestration framework can help coordinate multi-step model workflows. Neither removes the need for a clear contract, evidence checks, or failure handling. Add a dependency when its benefit is concrete.

</details>

## 4. Build a request from validated sources

Validate the input before paying for a model call. Our small app allows one to five records, each with a unique source ID such as S1 and a nonempty text field of at most 2,000 characters. Those are **application limits**, chosen for this exercise, not a model's token limit. A character count is not token accounting.

The request contains stable instructions, source data serialized with `json.dumps`, a JSON schema, and an output-token limit. **Serialization** converts a Python value into a transport representation. It correctly escapes quotes and newlines; it does not make hostile source instructions safe for a model to follow.

The following excerpt is from `build_request`; the complete schema is in the workbook:

```python
return {
    "model": model,
    "instructions": INSTRUCTIONS,
    "input": [{"role": "user", "content": json.dumps({"sources": sources})}],
    "text": {"format": {
        "type": "json_schema", "name": "study_suggestion",
        "strict": True, "schema": schema,
    }},
    "max_output_tokens": 1200,
    "store": False,
}
```

The schema requires all four recommendation fields, rejects additional properties, and limits `evidence_ids` to supplied IDs using an **enum**, a list of permitted values. The exam-date field permits a string or `null`. `null` means exam timing is not established here; it is different from the string `"null"`.

The local validator also checks nonempty strings and distinct evidence IDs. Even schema-constrained generation is only one layer: it cannot establish that the chosen source proves a claim. The exact request format and supported schema features are documented in [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

## 5. Make the service boundary explicit

The live adapter sends an HTTPS `POST` to the Responses endpoint. The JSON body contains the request; an authorization header carries the API credential. A **timeout** limits waiting on a network operation. The workbook passes 30 seconds to its HTTP transport; this is a network-operation setting, not a guaranteed 30-second deadline for the complete application.

```python
request = Request(
    ENDPOINT,
    data=json.dumps(payload).encode("utf-8"),
    headers={"Authorization": "Bearer " + self.api_key,
             "Content-Type": "application/json"},
    method="POST",
)
with self.transport(request, timeout=30) as response:
    return load_json(response.read().decode("utf-8"))
```

Read this as four transformations: Python dictionary → JSON text → UTF-8 bytes → HTTP request. The return path reverses that process into a response dictionary. The snippet shows the successful path; the actual adapter also handles HTTP errors, connection failures, and invalid response JSON. The [Responses API reference](https://developers.openai.com/api/reference/python/resources/responses/methods/create) defines the envelope and request options.

Notice the two JSON layers. The **API envelope** contains status and output items. One assistant output item contains **candidate recommendation text**, which must itself be parsed as JSON. Parsing the outer envelope does not validate the inner recommendation. Never assume the first output item is the answer: a reasoning item can appear before an assistant message.

## 6. Accept a draft only after distinct checks

The workflow applies checks in order, stopping at the first unusable result:

| Check | Failure example | App outcome |
|---|---|---|
| Input | No source records | invalid_input, zero provider calls |
| Transport/service | Credentials rejected or retry budget exhausted | service_error |
| Envelope | Incomplete response or refusal | incomplete or refused |
| Candidate JSON | Broken syntax, duplicate keys, NaN | invalid_json |
| Recommendation contract | Wrong types or unknown source IDs | invalid_recommendation |
| Evidence review | Supported structure but invented exam timing | Still review_required; human checks meaning |

An HTTP success status does not guarantee a complete model answer. If generation stops early, do not add a brace to the truncated text and call it finished. If the model refuses, handle that as a distinct outcome rather than parsing the refusal as recommendation data or trying to bypass it.

The application deliberately calls its accepted state **review_required**, never “verified.” In the unsupported-claim fixture, `exam_date` says 2026-12-01 and cites S1. S1 exists, but only states learner preferences; it says nothing about exam timing. The type and ID checks pass; the evidence claim fails.

<details className="optional-depth">
<summary>Go deeper: structured outputs, rendering, and actions</summary>

Our malformed and wrong-type fixtures deliberately inject bad outcomes. They test defensive application behavior; they are not measurements of how often schema-constrained models fail. A completed, non-refused response under a supported strict schema has stronger format guarantees, but can still contain incorrect values. Provider refusal and incomplete-response behavior must be handled separately.

Treat the candidate as data. Render text with an escaping UI mechanism; do not feed it into raw HTML, SQL strings, `eval`, or shell commands. This app grants no model-generated action permissions. It only prints a candidate and its status. If a future app saves a recommendation or creates a calendar event, the application must authorize that separate action and handle duplicate submissions.

</details>

## 7. Retry temporary failures with a budget

A **retry** repeats a request after failure. It can help when a service is briefly unavailable; it cannot repair an invalid credential or establish a missing fact. Two total attempts means the original call plus **one retry**.

<ApplicationDiagrams kind="retry" />

The workbook defaults to one attempt. With `--attempts 2`, it permits one retry for selected temporary server errors, connection/timeouts, or explicitly recognized rate-limit errors. Authentication errors, invalid requests, quota errors, unknown 429 codes, and content-validation failures stop. A 429 may mean throttling or a spending limit; inspect the provider's error code rather than treating every 429 alike. See the [official error-code guide](https://developers.openai.com/api/docs/guides/error-codes).

Before its one retry, the live adapter uses a one-second default wait or a numeric `Retry-After` delay of at most ten seconds. Longer or unrecognized delay instructions cause a stop so the caller can retry later. Offline mode records the same decision without sleeping. This tiny policy makes the attempt budget observable; it is not a complete high-volume retry system.

<details className="optional-depth">
<summary>Go deeper: backoff, deadlines, and uncertain outcomes</summary>

**Exponential backoff** increases successive waits, for example 1, 2, 4 seconds; **jitter** adds variation so many clients do not retry together. This workbook permits only one retry, so it has no growing sequence or jitter. A production system also needs a total deadline, concurrency limits, cancellation, and a deliberate policy for provider guidance.

A timeout means the client did not receive a usable answer in time. The service may still have processed the request. A retry can generate another response and another charge. If a workflow later performs an external action, a retry must not blindly repeat that side effect. **Idempotency** means repeating an operation has the same intended effect as doing it once; it needs explicit application or service support, not a prompt instruction.

If an SDK already retries requests, an outer loop can multiply the number of calls. Choose one place to own the retry policy and measure the actual attempts. An incomplete generation may need a different output budget, while malformed content may need a prompt or schema change; neither is automatically solved by a transport retry.

</details>

## 9. Test behavior, then evaluate useful answers

**Unit tests** check a small piece such as parsing or validation. A **workflow test** checks several pieces together with controlled dependencies. A **live integration test** checks whether the real provider connection works. An **evaluation** assesses the quality of outputs on task-specific cases. Keep these claims separate.

<ApplicationDiagrams kind="tests" />

The workbook tests zero calls for invalid input, a maximum of two calls for temporary failures, refusal handling, malformed output, field rules, and the known limitation of unsupported claims. Adapter tests intercept HTTP locally to inspect headers, request data, timeout settings, and error classification. They use a dummy credential and never call the service.

After choosing a live model, evaluate real outputs on varied study requests: supplied and missing exam timing, conflicting study-time estimates, changing preferences, and embedded instructions. Review factual support and completeness against sources, not exact wording. Keep some cases separate from prompt revision and repeat trials when response variability matters. Passing fixture tests is a prerequisite for that work, not evidence that the model is accurate.

<details className="optional-depth">
<summary>Go deeper: observability, cost, streaming, and state</summary>

**Observability** helps explain what the app did. The workbook records a prompt version, selected model label, attempts, outcome, and stage trace. These events exclude raw source bodies and credentials; the printed candidate is still content you must handle appropriately. A deployed service can additionally record request IDs, elapsed time, token usage, and failure rates with suitable access and retention controls. This workbook does not invent latency, token, or cost measurements for fixture runs.

For a simple uncached text request, a planning estimate is input tokens × input rate plus output tokens × output rate, using consistent pricing units. Actual billing can include cached-input rules, reasoning tokens, tools, and retries. Check the chosen model's current pricing and inspect returned usage; words and characters are not exact token counts.

**Streaming** delivers pieces as they become available. It improves perceived responsiveness, but an unfinished stream is not a validated recommendation. If you stream a draft to a UI, label it pending and wait for the final status before accepting it. The workbook uses a non-streaming request so the response boundary is easier to inspect.

**Conversation state** is the earlier information included or referenced in later calls. This app is intentionally stateless across runs: it sends the chosen sources each time and does not pass a previous response ID. A printed trace is not conversational memory. A future chat interface must choose what history to retain, how to bound it, and how to isolate one user's state from another's.

</details>

## 12. Keep the model call small and the application explicit

You now have an executable path from source records to a reviewable draft, with the service call isolated behind an adapter. The strongest practical habit is to name the guarantee at each boundary: valid input, completed response, valid JSON, accepted structure, and reviewed evidence are different achievements.
